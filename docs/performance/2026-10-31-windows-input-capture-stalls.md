# Windows 输入与关键帧停顿修复

用户反馈 GPU 编码版主要问题是卡顿。本轮先处理发布端已经复现的两处停顿，不据此认定网络、Mac 解码和呈现延迟已全部解决。

## 连续输入不能等待采集完成

发布端每处理 8 条请求就让视频分支运行，但旧代码只在视频定时器分支重置计数；采集未结束时该分支关闭。因此超过 8 条的输入会等待当前采集，编码器初始化的长停顿也会拖住鼠标键盘。

现在一次输入批次之后先让已就绪的采集结果和定时器运行，否则主动让出调度并恢复输入读取。仍保留批次数量限制，避免连续输入饿死视频。

实际配对 QUIC 回归测试将采集无限挂起，发送 32 次指针输入和文字提交。旧实现超过 500 ms 后失败；修复后整个集成测试约 0.4 秒通过。失败路径先释放采集任务，再报告断言，避免测试退出也被挂住。

## 重新同步保留硬件编码器

之前请求关键帧会销毁并重新发现、初始化编码器。本机真实窗口测试记录一次硬件初始化耗时 262 ms。现在仅在硬件编码器确认上一个输入已经输出、没有待取输出时，使用系统 `CODECAPI_AVEncVideoForceKeyFrame` 请求下一帧并更新流编号。

不支持该请求或仍有缓冲时继续重建。新流首帧必须具有匹配的时间戳、IDR NAL、SPS 和 PPS；如果驱动接受设置却未正确输出，现有软件回退会接管，不把依赖旧帧的输出发送为新流。软件编码器仍走原有重建路径，尺寸和帧率变化仍重建硬件编码器。这不是绑定某一厂商的优化，也不要求独显。

参考：[Microsoft 强制关键帧属性说明](https://learn.microsoft.com/en-us/windows/win32/medfound/codecapi-avencvideoforcekeyframe)。该设置为 VT_UI4，仅作用于下一个输入样本。

## 实测与范围

本机依次运行旧版、新版独立发布进程，采集同一人工动态窗口，使用本机管理通道，1602×932 源画面、60 fps、`444-atlas-v1`，读取 240 帧，每 60 帧主动请求关键帧。测试没有控制真实用户应用，不是跨 EasyTier 到 Mac 的端到端测试。

| 指标 | 旧版 | 修复版 |
| --- | ---: | ---: |
| 实际交付帧率 | 52.45 fps | 60.11 fps |
| 帧间隔 P95 | 20.15 ms | 19.24 ms |
| 帧间隔 P99 | 26.47 ms | 21.69 ms |
| 最大帧间隔 | 229.07 ms | 24.78 ms |

这是单次顺序对照，内容时序和系统调度存在差异，不将结果外推为实际远程体验的改善比例。`windows_stream_probe.ps1 -KeyframeEvery 60` 可复现关键帧压力。

额外验证：

- 320×180、1602×932、2560×1440 的普通/全色度硬件编码，各 120 帧、3 次原位重启；重启连同颜色转换及编码约 0.17–4.70 ms。
- FFmpeg 独立解码所有 6 个重启后的码流片段，无错误，不依赖之前的参考帧或参数集。
- 真实动态窗口经采集工作线程完成 120 帧及两次新流重启，日志确认硬件编码器保留。
- 强制关闭 GPU 合成并使用软件编码的全色度窗口测试通过；硬件故障注入后的软件回退测试通过。

新增编码器初始化耗时、帧率失效和关键帧重建原因日志，用于后续实际 Mac 会话继续定位。日志不记录窗口标题、输入内容或画面。
