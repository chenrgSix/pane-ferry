# Windows 每秒关键帧突发排查

用户在 BBR 对照后仍报告固定频率卡顿，要求先排除 Windows。
本轮发现发布端确有需要修复的大帧突发，不能据此前几轮编码耗时较低就认定 Mac 有问题。

## 隔离方法和证据

使用 `windows-video.ps1` 的连续动画，直接读取 Windows 发布端本机 IPC，
绕过 Mac、EasyTier 和 QUIC。WinForms 将请求的大窗口限制到实际 2566×1453；
4:4:4 载体为 4096×1822，不能将本轮描述为用户 4096×1740 场景的精确复刻。

最初 PowerShell 探针每秒显示 35–52 ms 间隔。随后新增原生
`apps/windows-node/examples/local_cadence.rs`，在 JSON 解析前记录数据到达时间，
并分开记录解析耗时、帧大小、关键帧标记。原生结果说明 PowerShell 放大了大帧解析耗时：
并非 Windows 采集线程每秒阻塞 50 ms；但编码器确实每 60 帧输出一次约 1.6 MB 的关键帧。

同一连续动画、60 fps、立即本地反馈，各读取 1800 帧：

| 测量 | 修复前 | CBR + 两帧 HRD 预算 |
| --- | ---: | ---: |
| 关键帧数量 | 30 | 30 |
| 普通帧/全体帧大小中位数 | 81,348 B | 97,200 B |
| 帧大小 P99 | 1,580,613 B | 186,447 B |
| 最大帧 | 1,593,855 B | 293,025 B |
| 总体平均码率 | 52.24 Mbps | 48.26 Mbps |
| 原生解析耗时 P99 | 414 µs | 123 µs |
| 原生交付间隔 P99 | 22.78 ms | 27.85 ms |

关键帧间隔常见值从约 20–24 ms 变为约 16–18 ms。
整个序列仍有非周期性的长间隔，整体 P99 未改善，不能声称本地帧调度全部优化完成。
本次目标是消除网络必须一次接收/重传的巨型关键帧，不改变关键帧频率来掩盖问题。
1.6 MB 单帧在 100 Mbps 理想链路上仅序列化就需约 128 ms；这只是算例，
不是对用户实际链路容量的测量。实机此前也有持续丢包和确认等待，仍需同场景复测。

## 实现和验证

原实现仅设置平均码率，未明确设置码率控制模式或短 HRD 缓冲预算。
现在在媒体类型协商前设置 CBR，以及按初始目标码率计算的两帧 HRD 字节预算。
保留平均码率、4:4:4、零 B 帧、原尺寸和硬件失败后的软件路径。
不满足这些标准控制的硬件候选会沿现有初始化失败路径回退，不绑定显卡厂商。

接口依据：[H.264 编码器](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-encoder)、
[HRD 缓冲区按字节设置](https://learn.microsoft.com/en-us/windows/win32/codecapi/avenccommonbuffersize-property)。
CBR 会重新分配各帧的码率，复杂画面的瞬时保真度仍有取舍，不等同于无损。

- Windows 完整检查通过。
- 实际硬件 GPU 输入、4:2:0 / 4:4:4、主动 IDR 恢复测试通过。
- 实际软件编码测试通过，包括 4096×1900 源画面的 4:4:4 载体。
- FFmpeg 独立解码 16 条合成流通过，包括可独立解码的重启后缀。
- 软件 4:4:4 输出逐像素检查红蓝交替图案，四色测试尺寸的红蓝分离最小值均超过 244，
  高于原回归的 180 阈值。此检查不代表所有真实文字或视频内容的视觉质量已验收。

复测本机实际发布节奏（须先运行专用动画测试窗口）：

```sh
cargo run --release --locked -p paneferry-windows --example local_cadence
```

可在最后追加隔离发布端状态目录。工具只选择名称完全匹配的合成测试窗口，
不保存画面、邀请码或键鼠内容；统计中的时间基准仅在本机使用。
