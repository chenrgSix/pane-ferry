# GPU 读回、快照复制与编码上传的进一步诊断

接续[上一轮对照](2026-10-28-further-optimization.md)，本轮拆出 GPU fence、CPU 复制、GStreamer 元件和 VA API 的耗时，
另做三组交错候选试验。**没有得到可部署的完整链路收益，正式 Agent 保持原版本。**

[机器可读统计](2026-10-28-gpu-readback-upload.json)、
[16 轮有效记录、VA 调用、失败预检、候选源码与检查日志](2026-10-28-gpu-readback-upload.raw.json.gz)。

## 测量边界

本机 Ubuntu / GNOME 50.1、内核 7.0.0-38、i5-13400 / UHD 730、GStreamer 1.28.2。
使用独立 GNOME/XWayland、DRI3 私有线性目标、自有 GTK 滚动窗口；2940×1618、60 FPS 上限，关闭视频反馈。
每轮预热 2 秒再测 8 秒，各组按旧、新、新、旧交错；采样不并行编译或运行其他基准，用户其他任务保持运行。
原分辨率、码率、QP 上限和 GOP 保留。

起点为读像素函数入口，终点为完整 H.264 JSON 行写入本机 Unix socket，不含此前应用绘制/等待采样、QUIC 或控制端显示。
读回 ID、消息 seq、消息字节数逐帧关联；pad 只观测原缓冲，不读画面内容。
线程 CPU 只在同一线程内做差，不包含转换器/x264 其他工作线程的 CPU 时间。
本轮负载波动明显，**不同诊断轮次的绝对数字不能相减为优化收益**；各行分位数也不能相加。

## 正式软编没有 GPU 编码上传

正式路径是 GPU → 不可变 BGRx 快照 → CPU 颜色转换 → CPU x264。
编码输入沿用已有快照租约，GStreamer 包装本身没有把画面上传回 GPU。
上轮约 16 ms 的“转换及编码调用”不能全部叫作 GPU 上传。

专门的 VA API 拦截仅用于实验硬编分支，不注入正式 Agent。
拦截保留参数、返回值及像素内容，只记录调用边界、线程、状态、对象 ID 和 image 字节数。

## GPU 完成等待和线程唤醒已经分开

读回仍按原顺序提交渲染、触发 XSync、确认目标导出、poll 等待、CPU START/END 同步并复制快照。
诊断额外导出该私有目标当前写 fence 的 sync_file，在原 poll 返回后查询内核 signal 时间。
它不设置 deadline、优先级或 GPU 频率，不改变原有同步条件。
同步语义参考 [Linux DMA-buf 文档](https://docs.kernel.org/driver-api/dma-buf.html)，
时间字段和状态来自本机 `linux/sync_file.h` 的公开 ABI。

| 区间 | 负载较重一轮 P50 / P95 | 后续复核 P50 / P95 |
| --- | ---: | ---: |
| 有效发布帧数 | 58 | 274 |
| 导出 → 内核 fence signal | 94.18 / 244.36 ms | **9.81 / 20.94 ms** |
| signal → poll 返回 | **0.031 / 0.055 ms** | **0.041 / 0.112 ms** |
| 19.03 MB 不可变快照复制 | 4.86 / 7.35 ms | 6.08 / 10.53 ms |
| 开始读回 → 本机写出 | 132.32 / 288.90 ms | 46.25 / 62.47 ms |

后续复核中，10 帧在导出时已经完成，导出后的等待记为 0，唤醒区间仅统计另外 264 帧。
已完成/retired fence 可能带很旧的 stub 时间戳，不能把它的年龄解释成线程唤醒延迟；汇总工具对此有专项检查。

两轮长短不同的等待主要发生在内核 fence signal 之前。数据支持 GPU 工作/排队是主要等待来源，
不支持把这部分解释为采集线程忙算或 poll 唤醒几十毫秒。
**fence signal 仍不等于某个 GPU 引擎的纯执行时长**，不能独立划分源窗口依赖、GPU 排队和实际复制执行。
设备级 perf 计数器因 `perf_event_paranoid=4` 不可用，没有修改权限来强行采集。

复核轮另以 0.5 秒采样 GPU 频率与部分限制状态：测量窗实际频率读数包含空闲 0 及 1350–1550 MHz；
热限制、PL1、PL2 采样值为 0，但总体限制状态出现过 1。
该采样不能覆盖每帧，也不能反推前一重负载轮的限制原因或宣称完全没有降频。

## 硬编上传成本确实存在，而且会出现在转换元件内

原实验硬编分支保留 CPU BGRx → I420，再交织 NV12、使用 VA 编码。
GStreamer 的下游 allocation query 会让转换器直接使用 VA 输入池，
因此映射/填充不一定发生在 `encoder.sink` 之后。
实现核对了 [GStreamer 1.28.2 VA allocator](https://github.com/GStreamer/gstreamer/blob/1.28.2/subprojects/gst-plugins-bad/gst-libs/gst/va/gstvaallocator.c)。

一轮有效诊断共 119 帧，观察到每帧约 7.25 MB 的 image 映射：

- `vaMapBuffer2(image)` 中位约 4 ms；不是只有一个几乎免费的取指针动作。
- map 返回 → unmap 入口的调用方填充中位约 2.60 ms；该区间包括转换器工作，不能称为纯 DMA。
- `vaUnmapBuffer(image)` 也有明显 CPU 开销，后续配对组中位约 2.10 ms。
- 编码提交后的 `vaSyncSurface` 中位约 8.72 ms，线程 CPU 中位约 0.034 ms，主要是等待。

以上是 API 服务时间与调用方区间，不能精确命名为驱动内部哪一次物理复制；有些 map/unmap 可能执行暂存或布局处理。
同一缓冲 ID 可在 image 销毁后被 coded output 重用，汇总按调用顺序区分两者，避免把码流读取误算成上传。

## 三组没有采用的候选

### 映射内存的 streaming load

对私有映射尝试 SSE4.1 `MOVNTDQA`，保留 GPU/CPU 同步、对齐处理、精确行尾和独立快照。
参考 [Intel 指令手册](https://cdrdv2-public.intel.com/868141/253667-089-sdm-vol-2b.pdf)；
该指令可能有利于 WC 内存，不能预设这台机器的映射一定受益。
填充、未对齐、奇数行尾和快照所有权检查通过，但真实映射对照更慢：

| 同轮指标 | 原实现 | streaming load |
| --- | ---: | ---: |
| 快照复制 P50 / P95 | **5.56 / 11.50 ms** | 6.54 / 13.41 ms |
| 开始读回 → 写出 P50 / P95 | 70.27 / 110.60 ms | 72.12 / 106.06 ms |
| 发布帧率 | 16.88 FPS | 17.19 FPS |

吞吐的小幅差异没有对应复制或整体中位延迟改善，未保留 SIMD 产品代码。

### 1× 时直接 XCopyArea

源/目标尺寸和 visual 相同才尝试 XCopyArea，其他情况保留 XRender。
该临时候选没有减少等待，发布 15.06 → 10.94 FPS，读回到写出 P50 / P95 从
77.15 / 123.23 → 100.70 / 147.19 ms。没有继续把它打磨为生产分支，也没有部署。

### CPU 直接生成 NV12、隔离 VA allocation query

以 CPU 直接 BGRx → NV12，并用 `identity drop-allocation=true` 避免转换器直接映射 VA 池。
既有解码画质/租约回归通过，但成本主要挪到编码器内部：

| 同轮中位区间 | 原实验硬编 | 隔离分配查询候选 |
| --- | ---: | ---: |
| CPU 颜色转换 | 6.02 ms | 5.85 ms |
| 编码器元件，含其内部上传 | 8.53 ms | 15.97 ms |
| VA image 映射调用 | 3.55 ms | 3.41 ms |
| 映射后填充 | 2.51 ms | 1.71 ms |
| VA image 解除映射 | 2.10 ms | 1.95 ms |
| 提交后 GPU 编码等待 | 7.87 ms | 7.86 ms |

NV12 交织元件本身接近零耗时并不意味着上传消失。
这组 GPU 等待很重：旧/新/新/旧 FPS 为 4.38、4.00、4.75、6.50；完整中位延迟没有改善。
保留全部轮次，不把相邻负载变化当作编码器的确定因果收益，未启用硬编。
