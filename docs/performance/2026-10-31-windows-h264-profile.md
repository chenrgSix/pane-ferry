# Windows 动态画面压缩效率

用户确认 df55e3d 流畅且不闪烁，但快速变化时仍见模糊/像素块。
现场日志的稳定播放约 60 fps，视频输出约 50–60 Mbps，目标恢复到
71.27 Mbps，反馈延迟常见约 30 ms。这一轮没有提高码率上限或恢复固定 QP 下限。

## 根因及实现

独立解析同一路 Windows 编码器的合成输出，发现实际 SPS 是 Baseline（66），
PPS 的 `entropy_coding_mode_flag` 为 0。原代码虽然想选择 High，但把
`CODECAPI_AVEncMPVDefaultBPictureCount=0` 设置失败直接解释为必须使用 Baseline。
本机硬件对该可选控制返回 E_INVALIDARG，读取也返回 E_NOTIMPL；媒体类型协商
前后均如此，不能据此认定 High 不可用。

现在优先协商 High，仅当 High 输出媒体类型确实失败时尝试 Baseline；High
可用时请求 CABAC，缺少此可选控制不阻止编码。不按显卡厂商分支。
仍设置低延迟、尝试禁用 B 帧，并强化运行时检查：每个硬件输入必须立即产生
一份对应当前输入时间戳的输出。需要后续帧才能输出、丢失匹配时间戳、积压或
重排序的硬件走既有软件回退，新流从 IDR 开始。软件仍显式要求零 B 帧。

依据：[微软 H.264 编码器及硬件可选接口](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-encoder)。
不把“设置成功”当作实际生效的证明：独立解析新版合成码流，确认 profile 100、
CABAC 标志 1；实际硬件探针逐帧输出、主动恢复和独立恢复后缀均验证。

## 相同目标码率下的合成对照

复用 `bitrate_adaptation_probe` 的确定性色块动画，源 2560×1440、444
载体 4096×1800、60 fps；高/低目标分别为 73.728/18.432 Mbps。
FFmpeg 解码后按 atlas 布局还原三个平面，与生成器的整数 YUV 参考比较。
在第 90/120/150 和 270/300/330 帧的动态区域按三像素步长采样。

| 编码 | 高目标实际码率 | 高目标 Y/U/V PSNR | 低目标实际码率 | 低目标 Y/U/V PSNR |
| --- | ---: | --- | ---: | --- |
| 原 Baseline | 72.76 Mbps | 49.75 / 51.95 / 49.57 dB | 17.52 Mbps | 20.06 / 20.23 / 26.56 dB |
| High + CABAC | 49.09 Mbps | 78.24 / 78.01 / 65.22 dB | 18.41 Mbps | 37.74 / 37.51 / 36.29 dB |

这是同一目标预算，不是严格相同的实际字节数。图案重复性高，改善幅度不能
外推为真实浏览器视频的提升百分比，更不能解释为无损视频。软件码率调整仍
通过：低目标实际约 16.13 Mbps。

## 真实采集路径及限制

WinForms 滚动夹具，经 WGC、GPU 合成、直接纹理编码、IPC，600 帧：

- 发布 2562×1432、载体 4096×1792，尺寸和 444 模式不变。
- 平均约 34.45 Mbps（此前同夹具约 38.62 Mbps），只有启动关键帧。
- 帧交付中位数 16.68 ms、P99 24.23 ms、最大 27.73 ms。
- 编码中位数约 6.6–8.8 ms，各窗口 P99 最大约 11.95 ms。
- 编码复杂度略有增加，不能承诺所有设备都保持相同速度。
- 注入硬件输入失败后，已验证软件新 IDR 流和后续帧正常输出。

Mac 协议、444 布局、目标码率和反馈算法均不变，需用户复测真实快动画的
清晰度及跟手程度；测试没有录制用户的应用画面。

Windows 完整检查通过。15 条合成码流及恢复后缀独立解码通过，共 21 个 I 帧、
2739 个 P 帧，没有 B 帧；这属于本机实测，不代替其他硬件的运行时延迟检查。
