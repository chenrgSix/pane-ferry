# 按 10.0.1.66 恢复复测与旁路计时

2026-10-26 晚，按用户指定的 `10.0.1.66` 恢复调查。当前生产 Agent 仍为已部署的
`bda43cf`，本轮没有更改生产 Mac、Agent、网络或 GNOME 扩展。

同一 IP 路径、1×、30 FPS 上限的无插桩正式对照，各版 240 个样本：

| 指标 | 选帧优化前 | 已部署的选帧优化后 |
|---|---:|---:|
| 中位数 | 102.326 ms | 93.063 ms |
| P95 | 151.890 ms | 127.491 ms |
| 最大值 | 235.258 ms | 166.405 ms |
| 低于 100 ms | 103/240，42.92% | 152/240，63.33% |

同轮中位数减少 9.264 ms / 9.05%，P95 减少 24.399 ms / 16.06%。
当前 P95 仍超过 100 ms，不能称为 95% 操作已低于 100 ms。

## 路径和方法

- Mac 路由确认 `10.0.1.66` 走 `utun4`。四次 ICMP 往返为 17.843–21.857 ms，平均 19.477 ms。
  这与之前 `192.168.1.254` 的局域网直连环境不同；不能直接与历史 69.4 / 100 ms 串算改善。
- 正式对照顺序：旧、新、新、旧、新、旧、旧、新；每轮 30 次方向键加 30 次点击。
  等首帧后等待 2 秒，每种输入排除两次预热。八轮均验证源输入计数、对应绘制、尺寸、硬解和时序。
  慢样本全部保留，P95 使用最近秩。
- 测试自建 Wayland 窗口，源 1470×809 像素、1×，接收窗口 1460×801 点，显示器 60 Hz。
  相同 H.264 参数、画面内容、约 30 FPS 小动画和发布上限。未提高帧率或降低编码质量。
- 临时网络实例使用现有配对身份、证书和相同网络二进制，实际连接日志确认
  `10.0.1.66:42974`。该端口属于隔离测试 Agent；生产网络和设备地址保持原状。
  SSH 仅负责管理夹具、取回日志，不参与输入/视频计时。
- 两个无插桩 Agent 仅通过私有状态目录与生产实例隔离，其生产代码分别对应优化前和 `bda43cf`。
  生产会话全程保留，未重启用户应用。
- 起点为 Mac SurfaceView 输入处理，终点为 AVFoundation 暴露与提交缓冲身份一致的显示缓冲，
  随后校验视觉计数。仍为 **renderer displayed-buffer availability**，不包含物理键鼠扫描、
  最终桌面合成、屏幕扫描和面板响应，也不是用户 ChatGPT/IDEA 业务操作的直接测量。

## 排查插桩是否改变结果

新增 `agent_stage_probe.py --trace-only`，将诊断阶段留在权限 0600 的本地 JSONL 中，
在序列化前移除 `_agent_stages`，写出后仅供旁路日志恢复。线上帧不携带诊断元数据；
通过帧编号与 Mac 回显关联。它仍有采集身份钩子、像素计数检查和计时成本，不能称为零扰动。

三种构建按正常、旁路、线上元数据、线上元数据、旁路、正常的顺序测试，各 80 个正式样本：

| 构建 | 中位数 | P95 |
|---|---:|---:|
| 无插桩正常版 | 99.210 ms | 136.054 ms |
| 仅本地旁路计时 | 95.895 ms | 131.702 ms |
| 帧携带诊断元数据 | 94.334 ms | 117.248 ms |

本轮没有复现“插桩后固有地减少约 50 ms”的现象。几毫秒的节拍扰动和运行波动仍存在，
因此性能结论仍采用后续无插桩对照，诊断数据只用来拆分阶段。
旁路组全部 80 个正式响应均通过帧编号、原始帧身份、视觉计数、时间顺序和线上字段缺失检查。

## 当前分段

旁路组 80 个样本的独立中位数，跨机器仅相减各机器内部的持续时间，不相减绝对时间：

| 阶段 | 中位数，ms |
|---|---:|
| Mac 输入处理 → 写出结束 | 0.214 |
| Agent 读入 → 分发 | 0.025 |
| 分发 → GTK 输入回调 | 5.539 |
| GTK 输入回调 → 绘制记录 | 2.354 |
| 绘制记录 → 首个匹配原始 sample | 14.043 |
| 首个匹配原始 sample → 匹配 I420 | 4.774 |
| 最终选中 I420 就绪 → 发布 | 7.877 |
| 发布 → 编码开始 | 0.105 |
| 编码 | 2.134 |
| 双向网络、桥接及序列化混合剩余段 | 31.513 |
| Mac 解析与硬解 | 2.253 |
| Mac 主线程选帧 | 0.062 |
| Mac 选帧 → renderer 缓冲匹配 | 10.188 |

“首个匹配 I420 → 最终匹配帧发布”中位数为 11.705 ms；与最终选中 sample 的 7.877 ms 起点不同。
从最终选中原始帧到写出的帧龄中位数为 22.647 ms。
这些是不同边界的独立分位数，不能相加成一条精确时间线。

Mac 显示段继续拆分：enqueue 约 0.063 ms，commit 约 0.047 ms，
commit 返回 → 事务完成回调约 2.526 ms，回调 → 主线程约 0.039 ms，
开始缓冲检查 → 身份匹配约 7.769 ms。当前没有主线程堆积的证据；
事务完成与缓冲匹配也不等于物理 presentation 时间。

旁路组实际写出 529 帧，写出时“已有更新完成帧却提交旧帧”为 0。
发布间隔最小 33.373 ms、中位数 34.254 ms；实际写出间隔最小 24.646 ms、中位数 34.444 ms，
任意统计的一秒窗口最多写出 29 帧。编码与异步写出会使相邻包间隔有抖动，
不能只根据最小包间隔判断发布上限。线上元数据组同样没有漏选，最多 30 帧/秒。

## 历史约 50 ms 的差异仍有边界

本轮生产小样本先测得中位数 82.474 ms，后续无插桩对照新版为 93.063 ms，
没有稳定复现此前 118.505 ms 的结果。此前同轮旧版也达到 124.616 ms，
不能把那组变化直接解释为新版从历史 69.4 ms 回退到 118.5 ms。

当前混合网络/桥接段 31.513 ms，比原先诊断记录约 11.052 ms 多约 20 ms，
与这次约 19.5 ms 的网络往返相符；**该混合段并非纯网络耗时，也不能解释原先同局域网内全部约 50 ms 的差异**。
历史慢轮没有同一帧的完整旁路记录，现有证据无法确定当时唯一原因；不能仅凭源端曾有 Java 活动就断言是负载。
如果同一路径再次稳定回到 118–125 ms，应使用现在保留的旁路计时抓到那次慢状态，再决定生产修改。
