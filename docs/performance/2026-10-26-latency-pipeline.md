# 场景元数据异步查询、CoreVideo 显示与 30/60 上限复测

2026-10-25 至 26，真实 Mac → Ubuntu → Mac 的 IDEA Git 日志右键菜单测试。
最终保留 30 FPS 发布上限：两组各 60 次正式样本，中位数分别为 137.058 ms、134.796 ms，
P95 分别为 167.165 ms、168.868 ms；本次未证明提高到 60 上限能带来明显收益。

## 已部署的改动

1. `c5c4c38`：将应用会话的 scope/scene/list 元数据快照移到独立 RPC 线程。
   采集线程轮询有界结果，不等待 GNOME 查询返回；输入命令在各次查询之间优先处理。
   沿用原来的认证桥接、授权范围与输入校验，没有按 IDEA 名称或菜单特判。
2. `9b333e3`、`8e91d92`：VideoToolbox 输出保留为 CoreVideo/NV12 缓冲，直接交给
   AVFoundation 视频层，正常播放不逐帧生成 CGImage。保留奇数尺寸的 clean aperture、
   等比布局、输入坐标、IME 叠层和 PNG 位图兼容路径。每次新建传输连接都会绑定可读通知，
   新帧不再等待定时轮询；定时器仍处理反馈和超时。
3. 通过 Agent 环境变量分别部署 30/60 FPS 上限，使用相同源画布复测，最终恢复 30。
   上限不是持续实际帧率；静态去重、自适应降帧和 60 Hz 虚拟输出均保留。
   分辨率、缩放和 QP 上限相同，但名义码率随协商帧率计算，不能称为完全相同码率的对照。

探索中还定位了一个会造成“重连后只剩一张旧图”的问题：无控制器时，GNOME 回收场景采集输出；
稍后复用相同 PipeWire 数字节点 ID，旧管线和缓存图像却仍被继续使用。
`288997c` 在恢复采集时清理旧管线、缓存和在途元数据结果，等新的授权快照后再建流；
替换节点尚未就绪期间保留本地窗口身份，不反复销毁重建 NSWindow。
显式刷新关键帧不会触发这项重建。

此前尝试过复制 PipeWire 缓冲及调整缓冲池，均没有解决该重连根因，已完整撤掉。
最终采集缓冲路径与本轮起点相同，不能将本次结果归因于这些试验，也不宣称全链路零复制。

## 条件与计时口径

- 同一个已运行的 IDEA 进程，单应用会话画面；只右键及 Escape，没有执行菜单操作。
- 源画布 2940×1618 像素、逻辑 1470×809、2× 缩放；右键源坐标 (1000,900)。
- 预览后确认菜单内部 ROI (1080,385,420,60)，两组相同；每组 2 次预热、60 次正式样本。
- 均为 H.264、VideoToolbox 硬件解码、一个本地场景窗口。服务端使用无计时插桩的正式 Agent。
- 正常配对 QUIC，实际路由 utun4/EasyTier；这是当前隧道路由的结果，不是直连 LAN 测量。
- 起点为 Mac `SurfaceView.rightMouseDown`；终点为 AVFoundation 返回与本次提交缓冲
  对应的 displayed pixel buffer（核对 CVPixelBuffer 身份或 IOSurface ID）的时间。
- 时间戳记录后，菜单探针直接将 ROI 缩为 16×16 再比对菜单预览和关闭基线；正常计时
  不逐帧回读整张图像。所有差值使用同一 Mac 单调时钟，P95 为最近秩。

新终点是 **renderer displayed-buffer availability**，不是旧位图路径的 `NSImage.draw` 返回。
它包含视频层调度的等待，不包含屏幕扫描和面板响应；探针轮询本身也有少量开销。
历史约 222 ms 的操作布局和终点不同，本轮没有同终点的旧构建正式基线，不能据此计算优化百分比。

## 最终正式构建数据

| 指标 | 30 FPS 上限 | 60 FPS 上限 |
|---|---:|---:|
| 正式样本 | 60 | 60 |
| 中位数 | 137.058 ms | 134.796 ms |
| P95 | 167.165 ms | 168.868 ms |
| 最大值 | 193.526 ms | 219.032 ms |
| 发送结束→匹配帧完整行收到，中位数 | 120.173 ms | 119.553 ms |
| 协议解析和解码，中位数 | 5.433 ms | 5.420 ms |
| 解码完成→主线程选帧，中位数 | 0.066 ms | 0.081 ms |
| 选帧→显示缓冲可用，中位数 | 11.919 ms | 10.193 ms |

各阶段中位数不能直接相加。到达 Mac 之前的一段仍占主要等待，包含输入传输、应用响应、
采集、编码和返回传输，不能将其全部解释为网络耗时，也不能从本轮软件时间戳精确拆分这几项。

另外用测试自有 GTK 持续动画窗口连接正式打包的 WindowHost 做了帧率观察：60 上限时标题
先后显示约 25/29 FPS，30 上限时约 28 FPS。它只是瞬时观察，不能作为平均吞吐测试，
也不代替上述输入延迟测量；没有观察到持续 60 FPS。测试窗口和自建服务已关闭。

## 失败与探索轮次

保存的数据包括早期缓存旧帧导致的重连失败、后来成功的探索轮次，以及最终两组。
`final-60-a` 在 27 个正式样本后 ROI 匹配超时：当时 ROI 跨菜单和变化的 Git 背景，
没有导出失败截图，因此不能确定原因，也不能把这次失败直接归为 60 FPS 传输故障。
该不完整轮次已保留，不参与完整轮次的统计。

最终两组更换为同一个菜单内部 ROI，并去掉全帧诊断回读后，均取得 60 个正式匹配样本。
其他探索轮次不混入最终对照。原始记录保留当前仍在磁盘的探索数据；早期被覆盖的临时文件无法恢复。
