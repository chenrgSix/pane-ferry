# X11 读回与输入分离：实现、对照和部署

通用优化已部署到 Ubuntu，保留 **1×、30 FPS**。正式交错对照各 240 条有效输入响应，
端到端 P50 **123.262 → 106.699 ms**，减少 **16.563 ms（13.4%）**；
P95 **170.174 → 150.757 ms**，减少 **19.418 ms（11.4%）**。**没有达到延迟减半。**

[统计、分段、最慢五条和部署校验](2026-10-27-x11-async-readback.json)、
[脱敏原始记录](2026-10-27-x11-async-readback.raw.jsonl.gz)保留最终比较、诊断、未采用的中间结果及作废试验。

## 条件和边界

- Mac → `10.0.1.66`，路由 `utun4`；本轮 4 次 ping RTT 为 **15.572–21.913 ms**，均值 **18.122 ms**。
  不与历史物理局域网或其他负载下的 69.4/73.6 ms 直接相减。
- 自有 GTK X11 输入计数夹具，每 33 ms 更新一小块动画。源保留 **2940×1618、2× backing**；
  接收 **1470×809、1×**，Mac 显示区 **1445×793 点、60 Hz**。
  编码质量、GOP、H.264、硬解和网络程序未改；没有修改用户应用的 DPI。
- 正式比较使用未插桩 Agent 的隔离实例，配对状态独立；SSH 只管理测试、取回日志，输入和视频走 QUIC。
  顺序为旧、新、新、旧、新、旧、旧、新；每轮键盘、点击各预热 2 次，正式各 30 次。
  没有丢弃尖峰、失败轮次或选择最好一轮。每条均核对源输入、视觉计数、尺寸、协商 30 FPS、硬解与最终帧 ID。
- 正式采样不并行编译或运行门禁。Ubuntu 的其他 Java、数据库和用户应用保持运行；
  记录到的每轮前后 1 分钟负载约 **5.45–10.1**，详见 JSON。
- 起点为 Mac SurfaceView 输入函数，终点为 AVFoundation renderer 返回对应 IOSurface 的显示缓冲身份匹配。
  **不包括外设、屏幕扫描、面板响应，不是 input-to-photon。**
- 两端各用自身单调时钟。混合残差用各自主机上的时长闭合计算；没有把跨主机绝对时间直接相减当作单向网络延迟。

## 实现

1. `56b5c1f`：所有 Agent X11 采集入口使用独立认证连接和读回工作线程。
   XRender、SHM/GetImage 回复等待、快照复制离开控制/会话锁；每后端最多一项在途读回，
   完成槽按窗口替换，保留总像素预算，完成 fd 直接唤醒控制循环。
   私有 Xvfb 和现有桌面 Xwayland 共用该机制，没有应用名判断。
2. 同一改动：提交前重新激活 Damage，捕捉期间的新变化继续保留；缩放、尺寸、隐藏、销毁、重连用 epoch 淘汰过期结果。
   帧持有不可变 Arc 快照，SHM 后续复用不会修改编码中的图像。关闭时只取消私有读回连接，不等待卡住的线程。
   像素读取前后仍校验 XRES owner 和 OS 进程身份。
3. `61a4d79`、`9a3086b`：读回已经按协商间隔准入，完成后无需再付一次完整帧等待；
   先消费完成的快照，再启动下轮读回。读回忙时暂缓额外窗口健康查询；输入自己的身份校验保留。
4. `67e2468`：单独搬线程仍无法避开输入函数内的 X11 同步查询。
   对提供已授权 GNOME 几何接口的后端，输入改用 **XRES/OS 身份批准后绑定的稳定 compositor 对象**确认目标和焦点，
   坐标也按该稳定对象定位。目标被替换、离开作用域、进程身份变化时拒绝；输入路径不按复用的 XID 自动重新绑定。
   键码在建立后端时读取，MappingNotify 使缓存失效。没有兼容接口时保留原 X11 校验路径。

这移除了 Agent 常见键鼠路径中等待采集回复的依赖，**不保证 X 服务、合成器或源应用本身永远不会等待**。
传统 X11 回退路径也仍可能等待服务器回复。

### 帧率约束核对

两版协商及诊断 QoS 目标都为 30。基线原本在采集调用开始时限帧，新版在读回准入时保留该约束。
诊断中最短采集开始间隔为 **33.438 / 33.494 ms**，平均读回速率 **25.90 / 25.15 FPS**，
平均编码消息速率 **26.02 / 25.09 FPS**。本轮收益没有通过提高采样频率获得。

编码、排队和写出时间存在抖动，两版相邻发送完成间隔都可能短于 33.33 ms；
诊断最短分别为 **13.64 / 9.50 ms**。30 FPS 是采样/协商上限，不是每个发送完成时刻的固定网格；原始分布在 JSON。

## 分段诊断

另测每版 40 条，启用旁路时间戳，**不混入正式 240 条比较**。以下是各段独立 P50/P95，单位 ms，不能相加。

| 输入函数执行 | 4.452 / 16.749 | 3.668 / 17.326 |
| Agent 收到 → 源应用收到 | 20.203 / 51.786 | 12.237 / 35.442 |
| 源应用收到 → 首次绘制 | 19.653 / 35.686 | 9.288 / 34.966 |

| 最终响应读回墙钟 | 21.937 / 39.011 | 22.831 / 47.517 |

| 最终读回完成 → 发布 | 0.065 / 0.120 | 0.625 / 16.752 |
| 发布 → 编码开始 | 0.039 / 0.414 | 0.032 / 0.061 |

新版控制线程包装已有快照只需约 **0.003 ms**；这不代表读回本身只需 3 微秒。
读回仍有约 **23 ms 墙钟、0.9 ms CPU**，主要成本仍是等待 X 服务完成；现有埋点不能唯一归因为 GPU、驱动或服务端调度。
输入函数 P95 仍有约 17 ms，完成帧发布也仍有约 17 ms 长尾，不能宣称输入全链路已无阻塞。

JSON 保留诊断最慢五条的输入 ID、首个响应读回 ID、最终读回 ID、首个及最终 RWP 帧 ID、两端时间线。
X11 此路径没有独立 I420 ID 埋点，留空；Frame 包装 ID 不冒充 I420 ID。
未插桩正式样本只保留真实存在的 Mac/源夹具记录，Linux dispatch/capture 及首个读回 ID 留空，没有补造。
