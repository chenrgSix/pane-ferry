## 原来的约 23 ms 主要在等什么

这次同时记录读回线程墙钟、线程 CPU、请求提交、服务端回复、GPU 完成和像素复制。
旧路径的等待主要发生在 **SHM GetImage 请求已经发出、服务端尚未回复**；线程 CPU 很低，不能把它解释成颜色转换或复制计算。
对 Xwayland 的短时系统调用跟踪观察到 `DRM_IOCTL_SYNCOBJ_WAIT`、`I915_GEM_SET_DOMAIN`，
采样也出现共享内存分配和页面初始化。它们支持“服务端 GPU 同步及暂存读回”的定位；采样量不足以精确分摊各项百分比。

跟踪是单独的诊断实验：9 秒系统调用跟踪和 8 秒 perf，不读取系统调用数据缓冲。
重叠的 60 条旁路诊断响应明确单列，不进入正式 A/B。没有修改系统跟踪权限、驱动或电源设置。

另做不带 strace/perf 的两版诊断，共 304 / 302 次原始读回：

| 读回部分 | 基线 P50 / P95 ms | 新版 P50 / P95 ms |
|---|---:|---:|
| 整个读回调用 | 9.559 / 21.805 | 8.834 / 20.512 |
| 等 SHM 服务端回复 | 8.745 / 20.858 | — |
| 提交并确认线性目标导出 | — | 0.091 / 0.176 |
| 等 GPU 完成 | 包含在 SHM 回复等待内，无法独立拆出 | 7.873 / 18.909 |
| 像素复制 | 0.675 / 1.338 | 0.694 / 1.297 |
| CPU 缓存一致性开始 / 结束，P50 | — | 0.007 / 0.005 |

各行独立分位数不能相加。历史“23 ms”来自之前不同负载的样本，这次基线中位数本身已降为约 9.6 ms，
**不能把 23 → 8.8 ms 全算成本次优化**。按输入匹配最终响应帧的诊断子集，读回中位数甚至是 12.149 → 13.094 ms，
也不能宣称每张响应帧读回都更快。GPU 完成等待仍占大头，复制仍约 0.7 ms。

## 通用实现及边界

按能力检测启用 DRI3、XSync 和 GBM 线性目标，复用本后端自己的输出缓冲，并保留既有 XRender 缩放和像素结果。
XSync 触发渲染提交，随后在已有的独立采集工作线程等待 DMA-buf GPU 完成，再做 CPU 一致性同步并复制为不可变的自有快照。
Xwayland 无需为每帧执行原来的同步 GetImage 暂存读回；输入控制线程也不等待该工作线程的 GPU 完成。
诊断新版 302 次读回全部实际进入线性路径。

这项实现不按应用名、PID 或显卡型号分支。缺少能力、像素格式不支持或映射读回失败时，继续使用原有 SHM 路径。
只映射私有输出目标，保留源窗口所有者校验、尺寸/代际失效和帧所有权；缩放保持 1×，没有增加采集或输出帧率。
这里仍有约 0.7 ms 的自有快照复制，**不是零复制，也没有消除 GPU 的实际工作**。

诊断中“Agent 收到输入 → 夹具收到输入”P50 / P95 为 4.135 / 12.033 → 3.085 / 6.380 ms，
“应用收到输入 → 绘制”P95 为 22.874 → 13.022 ms。
这与减少 Xwayland 主线程被同步读回阻塞的预期相符，但诊断只有每版 40 次响应，不能把正式 9.2 ms 收益精确归到单一阶段。

同步语义参考 [Linux DMA-buf 文档](https://docs.kernel.org/driver-api/dma-buf.html)；
[Xserver 上游 Glamor XSync 实现](https://github.com/mirror/xserver/blob/master/glamor/glamor_sync.c)用于核对触发时提交行为，
并非对安装版本逐行一致性的声明。真实 GPU 像素对照另外验证了此同步路径。
