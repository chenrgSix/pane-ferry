# 普通 1× 分辨率的 Mac → Ubuntu → Mac 延迟对照

2026-10-26。两组均连接当前已部署的正式 Agent，使用同一套当前 WindowHost 源码的临时计时副本，
通过临时探针分别请求 1×、2×，复现不同像素密度。安装包、服务和用户应用均未为此次测量重启。

1× 中位延迟为 **123.478 ms**，2× 为 **168.701 ms**；
本轮减少 **45.223 ms（26.8%）**。
P95 从 226.386 ms 降至 167.328 ms。
1× 最慢样本仍达到 884.830 ms，保留在统计中；本轮改善了典型延迟和 P95，仍存在偶发长尾。

## 条件与口径

- 源端为测试自有的原生 GTK Wayland 窗口，逻辑页面 1470×809；1× 编码画面 1470×809，
  2× 为 2940×1618。网格、文字采用相同逻辑布局，计数标记和每 33 ms 更新的小动画块保持固定物理坐标。
- Mac 两组内容区均为 1467×805 点，画面等比显示。1× 的奇数高度通过 H.264 单行补边及 clean aperture 处理。
- 两组都协商并确认 30 FPS 上限，使用 H.264 和 VideoToolbox 硬件解码，保留正常反馈自适应与静态去重。
  名义码率遵循同一生产算法、随像素尺寸变化；没有固定为相同码率。30/60 偏好和正式服务配置未更改。
- 原有配对 QUIC，实际路由仍是 utun4/EasyTier；没有切换为直连 LAN，也没有暂停用户后台负载。
- 交错顺序为 2×、1×、1×、2×、1×、2×、2×、1×。每轮重启自有夹具清零，先等待 2 秒，
  再排除每种操作 2 次预热，正式交替测方向键与点击各 30 次。每种密度共 4 轮、240 个正式样本。
- 起点为 Mac `SurfaceView.keyDown` 或 `mouseDown` 处理前的单调时钟；终点为 AVFoundation
  `displayedPixelBuffer()` 与当前提交的 CVPixelBuffer/IOSurface 身份相符的时间，随后才核对视觉计数。
  这是软件完整往返链路，不包含键鼠硬件扫描、系统输入派发、最终桌面合成、屏幕扫描或面板响应。
- 识别标记直接读取 NV12 亮度平面的 8 个点，正常采样不为识别生成整帧 CGImage。全部样本均匹配唯一计数、
  正确 H.264 尺寸及硬件解码标记；Ubuntu 原始日志逐轮核对 64 次有序输入、对应绘制尺寸和密度。
- 单独的 1× 预检 8 个有效样本未混入正式对照。八个正式轮次全部完成，没有丢弃慢样本或失败轮次。

输入传输、应用响应、采集、编码与回程，当前记录不能进一步定位到单独环节。

## 阶段观测

| 阶段中位数 | 2× | 1× |
|---|---:|---:|
| 输入处理开始 → 写出结束 | 0.292 ms | 0.288 ms |
| 写出结束 → 完整响应行收到 | 153.533 ms | 109.647 ms |
| 响应行收到 → 解析/解码完成 | 3.640 ms | 2.729 ms |
| 解码完成 → 主线程选帧 | 0.073 ms | 0.077 ms |
| 主线程选帧 → 显示缓冲可用 | 8.789 ms | 8.799 ms |

Ubuntu 同端的输入回调到对应绘制结束，中位数从 7.460 ms 降至 2.182 ms。
这些阶段的中位数不能直接相加；源端绘制是响应链路中的子区间。主要差异位于画面返回 Mac 之前，
Mac 解码阶段略有缩短，显示层调度中位数接近。没有用两台机器的绝对时钟相减，也没有把整个往返区间归为网络延迟。
