# 输入到 Mac 画面绘制的实机延迟

2026-10-21，代码基线 `54e9df0`，Apple Silicon Mac / Ubuntu 26.04.1。

高清窗口确实有明显延迟。本轮当前自动窗口尺寸 2940×1612 的中位数约 **149ms**，P95 **221ms**。
主要时间花在 Ubuntu 产出新画面，另有传输/缓冲造成的偶发长停顿。

## 方法与范围

使用独立 HOME、catalog、Agent、Xvfb 和 GTK 编辑器，不操作现有 ChatGPT/Firefox，不替换安装包或重启用户服务。
测试副本从产品 `SurfaceView` 的方向键、文字提交和点击处理函数进入，经过现有 SSHTransport、X11 输入、
窗口捕获、GStreamer/OpenH264、VideoToolbox、60Hz inbox pump 和真实 NSView 绘制。
远端每次输入改变 8 位黑白标记；只有 Mac 绘制了相同输入 ID 的图像才记为完成。
所有有效样本均为 H.264，实际硬件解码属性为 true。

5 组各 90 个有效样本，每组方向键、文字提交、点击各 30 次，另排除各 2 次预热，共 **450 个有效样本**。
输入间有随机间隔。持续更新模式每 33ms 改变一个小块；静止模式只在输入后改变画面。
正式采样前修正了夹具的 GTK/GDK 版本、额外双击通知和非测试输入干扰；未通过校验的试跑没有计入数据。

起点是输入进入 AppKit 处理函数，文字从本地 IME 已提交后开始；终点是 `NSImage.draw` 完成。
未测键盘硬件扫描、系统输入派发、拼音组合时间、macOS 最终合成、屏幕扫描和面板响应，不能称为 input-to-photon。
测的是相同产品链路上的自有测试窗口，不是现有 Firefox 页面或 ChatGPT 的专属应用性能。
不同轮次顺序执行，后台应用与网络负载有变化；它是实机诊断，不是严格控制负载的路由 A/B 或生产验收。

## 总耗时

单位 ms。P95 使用最近秩；每组 90 个样本，不能把它解释为长期服务保证。

| 地址路径 | 远端像素 | 画面状态 | 中位数 | P95 | 最大值 |
| --- | --- | --- | ---: | ---: | ---: |
| 虚拟网卡 utun4 | 2940×1612 | 持续更新 | 149.05 | 220.57 | 280.38 |
| 虚拟网卡 utun4 | 2560×1664 | 持续更新 | 123.58 | 176.50 | 212.02 |
| 虚拟网卡 utun4 | 1280×832 | 持续更新 | 83.69 | 126.85 | 147.53 |
| 虚拟网卡 utun4 | 2560×1664 | 静止窗口 | 106.94 | 171.69 | 644.72 |
| 物理 LAN en0 | 2560×1664 | 持续更新 | 139.93 | 255.81 | 301.53 |

2560×1664 持续更新时，按键、文字、点击的中位数分别为 126.36 / 125.06 / 118.54ms，
三种输入都承担类似的后续画面成本。

## 慢在哪

以下是 2940×1612 持续更新组的**平均**阶段耗时，可加总回平均总耗时约 156.35ms。
每阶段的中位数不能直接加总成总耗时的中位数。

| 阶段 | 平均耗时 | 含义 |
| --- | ---: | --- |
| 两端输入内部处理 | 6.54 | Mac 发送队列、Agent 调度、X11 交付；网络另计，中位数 1.52ms |
| 应用响应到采集完成 | 42.56 | GTK 重绘、等下一次采集、X11 读整窗像素 |
| 等待编码及编码 | 64.46 | 排队约 16.11ms，编码通路约 48.13ms，少量回包准备 |
| SSH / 网络 / 读端缓冲 | 21.25 | 往返剩余时间，含桥接、socket 写出、流读取缓冲与少量序列化 |
| Mac 解码到绘制 | 21.53 | JSON/base64/VideoToolbox/图像准备 10.78ms，等主线程 8.57ms，绘制 2.17ms |

Ubuntu 的新画面产出合计约 **107ms，占平均总耗时 68%**。
虽然网络上传 H.264，远端仍轮询读取整窗原始像素，再经过进程间传输、拷贝、颜色转换和软件编码。
2940×1612 每帧原始 BGRx 约 18.1MiB；这里测到的“编码通路”包含这些准备成本，不能全归为 OpenH264 算法本身。

2560×1664 降到四分之一像素量的 1280×832 后，编码通路中位数从 38.19 降至 9.06ms，
编码等待从 15.70 降至 0.02ms；总耗时中位数从 123.58 降至 83.69ms。
这支持像素处理/编码是高清场景的主要瓶颈。静止窗口的编码等待也降至约 0.02ms，
但仍要承担约 30ms 的响应到采集、约 30ms 的编码，以及传输和本机呈现。

## 网络和偶发停顿

本轮实际路由显示：Mac 到 `10.0.1.66` 经过 `utun4`；Ubuntu 的该地址属于 `tun2`。
Mac `en0` 与 Ubuntu 的物理接口另有同网段地址，直连目标为 `192.168.1.26`。
物理地址登录使用原连接已验证的主机密钥校验同一台机器；没有关闭主机密钥检查。

20 次 ping 中，虚拟地址平均 14.07ms、最高 46.01ms、2 次无回复；物理地址平均 7.76ms、最高 16.80ms、无丢失。
这是 ICMP 观测，不能直接等同于视频 TCP 的丢包率。
2560×1664 持续更新组中，传输/缓冲 P95 从虚拟路径的 61.50ms 降至直连组的 24.90ms，
但直连组的远端采集和编码更慢，整体中位数没有改善，不能承诺换地址就能解决全部延迟。

静止组最长一次为 644.72ms，其中 553.45ms 位于传输/缓冲剩余段；对应回包仅 980 字节，且不是关键帧。
所以偶发长停顿不能简单解释成“大图片/大视频包太大”。尚未抓包，未区分网络排队、TCP 重传、SSH 多路复用
或读端缓冲各自的贡献，也未同步两端时钟来拆分上/下行。

优先优化远端采集调度、整帧拷贝及编码吞吐，再减少 Mac 60Hz 轮询等待；同时处理虚拟链路的尾部波动。
本轮仅增加测量工具和记录，产品及正在使用的远端会话保持原版本。
