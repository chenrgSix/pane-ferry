# SSH / 原生 QUIC 双机吞吐与路径诊断（2026-10-22）

结论：**当前最大的限制在 EasyTier 虚拟链路；物理直连还发现了 Mac UDP 接收缓冲区丢包。没有证据支持“QUIC 一定比 SSH 慢”，也不足以据此删除 SSH。** 同一文件走物理地址可达数十 MB/s，走虚拟地址约 5–6 MB/s。关闭 EasyTier 的 QUIC 代理没有解除这个限制。仅增大临时 Mac QUIC socket 的接收缓冲区明显减少了直连丢包，但没有得到稳定的绝对速度提升，因此未将试验参数写入产品。

完成 **78 次有效网络/文件测试、26 组各 3 次**，另有两端各 3 次文件读写基线。48 次文件传输全部通过 SHA-256 校验。6 次物理 UDP 初始化失败样本单独保留并排除，修正绑定后已补足三次有效样本。所有实验在真实 Mac 与 Ubuntu 之间完成，不是回环测试；不代表桌面视频 E2E、长时间稳定性或 CI 已通过。

## 1. 对齐条件

| 项目 | Mac | Ubuntu |
|---|---|---|
| 系统 | macOS 27.0.1，26A434，arm64 | Ubuntu 26.04.1 LTS，Linux 7.0.0-38-generic，x86_64 |
| CPU / 内存 | Apple M4，10 核 / 10 线程，24 GiB | i5-13400，10 核 / 16 线程，系统报告约 61.5 GiB |
| 网卡 | en0，Wi-Fi 802.11ax，5 GHz / 160 MHz；初始协商 1729 Mbps | enp1s0，有线 1000 Mbps 全双工；r8169 / PCI 10ec:8168 |
| 物理地址 | 192.168.1.80/24，MTU 1500 | 测试使用 192.168.1.26/24；同网卡另有 192.168.1.254/24 |
| 虚拟地址 | 10.0.1.253/24，utun4，MTU 1360 | 10.0.1.66/24，tun0，MTU 1360 |
| SSH | OpenSSH 10.3p1 / LibreSSL 3.3.6 | OpenSSH 10.2p1 / OpenSSL 3.5.5 |
| 文件位置 | APFS /private/tmp，发送前读入缓存 | /tmp 为 tmpfs，发送前读入缓存 |

两端 EasyTier 均为 `2.6.4-8428a89d`。Rust 编译器分别为 Mac 1.97.1、Ubuntu 1.93.1。iperf3 均从同一官方 `3.22` 源码构建（静态库、无 OpenSSL 认证）。产品测试基线为仓库 `5028234` 的临时 release 副本，Quinn 0.11.12、quinn-proto 0.11.19、Tokio 1.54.0、rustls 0.23.46；只添加只读统计。原生 QUIC 使用 TLS 1.3、默认 CUBIC，单流接收窗口 4 MiB、连接接收/发送窗口 16 MiB。

文件是同一份 **134217728 字节（128 MiB）随机数据**，SHA-256 为 `79e453ffd533e17e984d1390c28d3d4af679c951495441d7db98698fc9c90f7b`。SSH 使用持久连接中的原始 stdin/stdout 管道及 C 文件端点，不是 scp/sftp；QUIC 使用产品 `bulk-upload` / `bulk-download` 和相同 C 端点。两者均无压缩、并发为 1；SSH 日志确认 `chacha20-poly1305@openssh.com`、`compression: none`。EasyTier 两端目标网络保存配置均未显式启用压缩，该版本默认 `none`。数据方向以文件字节流为准，两个方向均由 Mac 发起控制连接。

文件计时含每次 CLI/会话打开、传输和接收端 `fsync`，不含首次认证/配对及计时后的 SHA-256 校验。每轮按 SSH→QUIC、QUIC→SSH、SSH→QUIC 交错执行。MB/s 统一为 10⁶ 字节/秒。128 MiB 文件结果属于短传输，不能与 30 秒 iperf3 数值直接等同；两者都保留原始时间。

未停止用户其他应用。代理关闭后的文件组，Mac 整机忙碌约 21–44%，Ubuntu 约 3–6%；全矩阵 Ubuntu 整机忙碌范围约 2.4–19.2%。Wi-Fi 和背景负载会使不同时间段的成绩波动。早期样本只有 Mac 逐线程 CPU，没有整机 CPU ticks；缺失字段没有补造。

## 2. 实际路径与代理

- Mac `route get 192.168.1.26` 为 en0；Ubuntu 到 192.168.1.80 为 enp1s0。SSH 物理地址必须通过与虚拟地址相同的已知主机密钥，确认是同一台 Ubuntu。原生 QUIC 的诊断记录包含实际对端地址和隔离配对身份。
- Mac `route get 10.0.1.66` 为 utun4，Ubuntu 到 10.0.1.253 为 tun0。EasyTier GUI 在基线、关闭代理、恢复后均显示目标 Ubuntu 为 **p2p / udp**。
- 初始 Mac 配置：QUIC 代理开启，KCP 代理关闭，禁用 QUIC 输入开启，多线程开启，加密开启，实例接收限速为 0。开关实验**只改 Mac 的“启用 QUIC 代理”**；Ubuntu 保存配置为 QUIC 代理开启、QUIC 输入允许、KCP 代理关闭、用户态协议栈开启；其配置和其他参数不变。
- 开启时，Ubuntu iperf3 的 TCP 对端是本机虚拟地址 `10.0.1.66`；关闭后恢复为真实远端虚拟地址 `10.0.1.253`。这证实 TCP 连接被代理接管及开关实际生效。普通模式没有可用的 CLI 管理入口，未取得 `proxy` 的 `transport_type` 明细；QUIC 类型由已核实配置与该唯一开关对应，不能把配置截图本身当完整连接日志。
- EasyTier 的 QUIC 代理处理 TCP；应用原生 QUIC 本身是 UDP。因此“SSH over EasyTier QUIC proxy”与“原生 QUIC over EasyTier”经过不同处理链。见 [EasyTier 官方代理说明](https://www.easytier.cn/guide/network/kcp-proxy.html)。
- 同机还运行 Clash；测试物理地址的路由没有经过它的虚拟接口。未取得外层 UDP 逐包轨迹，不能进一步证明 EasyTier 的 P2P 外层必定使用私网地址、没有公网回环。GUI 的 P2P 标签说明没有显示中继，不等于已经完成外层五元组验证。系统不允许当前用户打开 BPF，`tcpdump` 返回权限不足；`nettop` 对其未连接 UDP socket 只给出 `*:*`。

## 3. 网络基础吞吐

TCP 使用 `iperf3 -P 1 -t 30 -J --get-server-output`，反向加 `-R`；每方向、每条件各三次，取接收端吞吐。

| 条件 / 数据方向 | 三次 MB/s | 中位数 MB/s |
|---|---:|---:|
| 物理直连，Mac→Ubuntu | 53.70 / 38.73 / 48.33 | 48.33 |
| 物理直连，Ubuntu→Mac | 48.26 / 45.41 / 47.35 | 47.35 |
| 虚拟 / 代理开，Mac→Ubuntu | 5.96 / 4.55 / 4.75 | 4.75 |
| 虚拟 / 代理开，Ubuntu→Mac | 6.10 / 5.98 / 6.20 | 6.10 |
| 虚拟 / 代理关，Mac→Ubuntu | 4.70 / 5.47 / 5.39 | 5.39 |
| 虚拟 / 代理关，Ubuntu→Mac | 5.72 / 5.40 / 5.38 | 5.40 |

关闭代理并没有把虚拟链路恢复到物理链路的吞吐。物理 TCP 本身未满千兆且有波动，但仍明显高于虚拟路径；当前不能优先把 5–6 MB/s 归因于文件程序或加密速度。

UDP 辅助测试：单流、每次 10 秒、目标 **12.5 MB/s**、1200 字节 UDP payload。它不包含 QUIC，不能当 QUIC 性能成绩。

| 条件 / 数据方向 | 三次 MB/s | 中位数 MB/s |
|---|---:|---:|
| 物理 / 显式绑定，Mac→Ubuntu | 12.49 / 12.50 / 12.49 | 12.49 |
| 物理 / 显式绑定，Ubuntu→Mac | 12.50 / 12.50 / 12.50 | 12.50 |
| 虚拟 / 代理关，Mac→Ubuntu | 6.60 / 6.64 / 6.59 | 6.60 |
| 虚拟 / 代理关，Ubuntu→Mac | 6.85 / 6.47 / 6.87 | 6.85 |

物理 UDP 六次中五次报告零丢包，另一次为 **23/104247（0.022%）**。虚拟 UDP 的接收有效吞吐约为目标的 53–55%；Mac→Ubuntu 三次接收侧报告丢包 **46.60%、46.25%、46.58%**，说明限速/拥塞/丢包已经存在于原生 QUIC 之外。反向 UDP 的发送端结束时间被拥塞中的控制连接拖长，iperf3 汇总的发送与接收统计区间不同；其 `lost_percent` 不直接用于双向比较，原始计数完整保留。

最初物理 UDP 使用通配监听而无法建立：Ubuntu 同网卡双 IP、回程默认源为 .254，目标是 .26。改为服务器 `-B 192.168.1.26` 后成功。这是**测试初始化条件修正**，不是一次网络速度优化，六个失败样本没有记成 0 MB/s。临时服务重启另有一次等待旧 socket 的夹具竞态，在开始文件计时前失败；修正等待条件后重跑，未计入协议传输失败或有效样本。

## 5. CPU、磁盘与丢包证据

采样间隔约 1 秒。Linux 用 `/proc/<pid>/task/<tid>/stat` 差分并补充 `top -H`；Mac 用 `ps -M`。100% 表示一个逻辑核。下表为对应组内观测到的相关进程最大**单线程**占用，不是整机平均。

| 条件 | Mac SSH / 原生 QUIC | Ubuntu SSH / 原生 QUIC | Mac EasyTier |
|---|---:|---:|---:|
| 物理直连，基线文件 | 38.7% / 25.9% | 14.0% / 12.0% | ≤7.5% |
| 虚拟，代理开，文件 | 12.9% / 9.1% | 3.0% / 5.0% | ≤33.0% |
| 虚拟，代理关，文件 | 13.2% / 10.6% | 6.0% / 5.0% | ≤23.1% |

未观察到相关线程持续跑满，因此没有证据要求先做加密/拷贝 CPU 火焰图。短传输和一秒采样无法排除很短的调度停顿。

磁盘与缓存：Mac 基线采样的整盘总 I/O 为约 0.4–45.0 MiB/s（物理文件组）；虚拟组最高约 68.0 MiB/s，含其他应用读写。Ubuntu NVMe 读约 0–0.04 MB/s、写约 1.17–2.20 MB/s、忙碌约 6–9%，其测试文件位于 tmpfs。后续独立文件端点基线如下，均包含程序启动，写入包含 `fsync`：

| 端点 | 三次读取 MB/s | 三次写入 MB/s |
|---|---:|---:|
| mac | 196.27 / 8034.88 / 10549.19 | 561.09 / 371.26 / 344.75 |
| ubuntu | 8911.95 / 9721.75 / 9251.93 | 3010.18 / 2704.79 / 2903.23 |

读取存在明显缓存效应；这不是两端冷盘吞吐测试。但相同文件端点的能力足以超过虚拟传输约 5–6 MB/s，故本次没有磁盘瓶颈证据。资源采样窗口含测试前后等待，整盘计数也包含背景流量，不与短文件计时直接等同。

物理网卡错误计数没有出现对应的大幅增长。Mac en0 的 Drop 增量各次为 0；Ubuntu enp1s0 的 `rx_dropped` 通常按约 0.2 包/秒增加，物理和虚拟测试都有，单次约 0–9 包，远小于 QUIC 的几千个判定丢包。驱动计数不能替代 Wi-Fi 空口重传统计。

原生 QUIC 在虚拟路径、代理开时，数据发送端三轮判定丢包比例分别为：Mac→Ubuntu **2.18%、2.09%、2.20%**；Ubuntu→Mac **4.10%、2.59%、1.79%**。对应传输结束时拥塞窗口仅约 **28–77 KB**，RTT 约数毫秒，且发生数百次拥塞事件。相对 4 MiB 单流窗口，首先应查链路丢包和拥塞响应。流控 `stream_data_blocked` 也有增长，但计数不是阻塞时长，不能仅凭计数认定流控窗口就是瓶颈。JSON 中保留逐秒 RTT / cwnd / MTU 与前后累计计数。

两端 UDP 缓冲计数均采集。部分 Linux `SndbufErrors` 增长可能是发送背压，不能直接当作不可恢复丢包。虚拟上传某次有 39 个 `RcvbufErrors`，其他同组为 0，不能解释每次约两千个 QUIC 判定丢包。更明确的本机证据来自下一组物理下载实验。

## 6. 单因素修改前后

### A. EasyTier QUIC 代理开 → 关

只改 Mac 当前网络的代理开关，其他配置不变；新 TCP 会话的对端地址改变，证实生效。TCP 中位数从 **4.75 / 6.10 MB/s** 变为 **5.39 / 5.40 MB/s**（Mac→Ubuntu / Ubuntu→Mac），没有解除虚拟链路限制。原生 QUIC 文件中位数从 **5.22 / 5.45** 变为 **5.56 / 5.75 MB/s**。开关应用会重建 EasyTier 网络，Wi-Fi 和背景负载也会变化；不能把这些小差异全部归因于开关。

### B. 只把临时 Mac QUIC socket 接收缓冲区增到 4 MiB

系统默认接收缓冲区为 786896 字节。原始物理下载三轮中，**Mac UDP 满缓冲丢包增量与 Ubuntu QUIC 判定丢包数完全一致：964 / 55 / 682**。这是本地接收缓冲不足的直接证据。

在 EasyTier 已恢复原设置后，临时 Mac 测试二进制仅设置 `SO_RCVBUF=4194304`，`getsockopt` 确认生效。没有改系统 sysctl、Linux 二进制、流控窗口、CUBIC、MTU 或文件端点，同时重新测 SSH 作为当时环境对照。

| 条件 / 数据方向 | 三次 MB/s | 中位数 MB/s |
|---|---:|---:|
| 4 MiB 实验 / SSH，Mac→Ubuntu | 62.87 / 55.74 / 80.27 | 62.87 |
| 4 MiB 实验 / SSH，Ubuntu→Mac | 65.76 / 79.73 / 86.90 | 79.73 |
| 4 MiB 实验 / QUIC，Mac→Ubuntu | 56.80 / 71.74 / 64.10 | 64.10 |
| 4 MiB 实验 / QUIC，Ubuntu→Mac | 80.81 / 76.04 / 69.02 | 76.04 |
Mac 满缓冲丢包和对应 QUIC 判定丢包变为 **0 / 0 / 9**，从合计 1701 降为 9，减少约 **99.5%**。但 QUIC 下载中位数从 84.96 变为 76.04 MB/s；同时 SSH 下载中位数也从 99.50 变为 79.73 MB/s。**本次证明减少了缓冲区丢包，没有证明稳定提高绝对吞吐。** 不将结果包装为已完成性能优化，不直接把试验参数推入产品。

## 7. 判断与剩余范围

1. **网络路径是当前首要限制。** 物理/虚拟的 TCP 与文件差距均很大，定速 UDP 在虚拟路径同样受限。应先确定 EasyTier 外层 UDP 是否绕公网、是否遇到路由器 UDP 限速/丢包，以及 EasyTier 内部队列/调度是否丢包。当前证据还不能在这三个更细的原因之间定案，也不能声称 EasyTier 代码本身有缺陷。
2. **协议实现存在已证实的可优化点。** Mac socket 接收缓冲区在直连突发流量下丢包；4 MiB 实验缓解丢包，但还需固定背景负载、更长的文件和真实窗口尾延迟对照才能决定产品参数。
3. **本次没有文件 I/O 或 CPU 饱和证据。** 未覆盖真实文件目录/剪贴板打包、H.264 媒体流桥接的所有开销；不能据此宣布应用层完全没有问题。
4. **保留 SSH。** 本次是短时吞吐与完整性检查，48 次文件校验成功不等于长时间运行、睡眠唤醒、切网重连、多设备并发都已通过。后续优先对齐物理地址进行同一场景的桌面延迟/稳定性验收，再决定是否删除兼容通道。

实验结束后，EasyTier QUIC 代理已恢复开启；Ubuntu SSH 与原 `remoteapp-agent.service` 正常，Mac 共享仍开启。产品源文件和已安装二进制未修改。本报告提交的是诊断夹具、数据和证据。
