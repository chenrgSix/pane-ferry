# 已部署 Agent 的 Mac→Ubuntu→Mac 实测（2026-10-24）

新版 `cf7d76a` 已部署，但这次没有获得整体端到端改善。静止场景的输入响应反而约慢
33 ms；持续重绘场景的中位数基本持平，P95 较低，但轮次间波动较大。
此前裁剪/转换/编码微基准的改善不能代替这个结果。

## 方法与范围

- MacBook Air M4，24 GB，macOS 27.0.1；Ubuntu 26.04.1 / i5-13400 / GStreamer 1.28.2。
- 复用现有配对和实际运行的 QUIC 网络服务；SSH 仅管理进程、部署和取回日志，不传测试输入/视频。
- Ubuntu 正常 GNOME Wayland 桌面中的测试自有 GTK 窗口，2940×1618 像素、2× 源缩放；不是 Xvfb。
- 使用当前 WindowHost 源码的独立 release 探针，保留真实输入处理、协议、VideoToolbox 硬件解码、
  inbox pump 和 AppKit 绘制路径。服务端部署的是无计时插桩的正式 release 二进制。
- 方向键与点击交错；各预热 2 次后各测 40 次，每轮 80 个有效样本。两次输入之间随机等待
  80–145 ms，必须绘制出匹配该输入序号的黑白标记才算响应。
- `idle` 只在输入时重绘；`animated` 每 33 ms 重绘，文字/图形主体不变，小色块持续变化。
- 起点是 Mac `SurfaceView` 输入处理函数，终点是对应图像 `NSImage.draw` 返回。
  **不含硬件输入、macOS 最终合成、显示扫描和面板响应，也不是 IDEA 本身的精确延迟。**
  所有总耗时使用同一 Mac 的单调时钟，不相减两台机器的时间。

脚本与复现说明：[tests/performance/README.md](../../tests/performance/README.md)。
探针提交 `6a8086a`；生产代码本轮未改。新增脚本 Python 语法检查、Swift release 构建通过，
真实运行核验所有正式样本的 H.264、硬件解码、输入种类/计数以及远端绘制尺寸/缩放。
此前 `cf7d76a` 的完整项目门禁见 [crop 报告](2026-10-24-pipewire-crop.md)；本轮没有重新跑全套门禁。

2940×1618、2×。两次各 6 样本的冒烟测试也未计入正式统计；失败与冒烟数据均保留。

## 能定位到哪里

Mac 侧时间戳显示，静止场景增加的时间主要发生在协议写出后、完整响应帧进入解析前。
该区间包含 Ubuntu 输入处理/应用重绘/采集/转换/编码、往返网络及本地桥接和缓冲，
**不能直接归因于裁剪转换或某个队列**。Mac 解码、主线程等待和绘制没有解释约 33 ms 的增量。
本轮没有服务端细分计时，尚未证实具体原因；未按猜测修改调度逻辑。

用户提供的 IDEA 小浮窗截图还暴露了另一个分类问题：当前 GNOME 描述未传递具体窗口类型，
Agent 将选中主窗以外的 transient 一律标为 `dialog`，并为它建立独立 PipeWire 捕获；
输出按 window ID 建立编码器。Mac 只有 `popup` 使用无边框样式，所以提示浮窗也会带标题栏。
它可能造成额外的捕获/编码生命周期，但截图不能证明新增了操作系统进程，也未测出其延迟贡献。
上述 GTK 正式测试每轮只有一个窗口，因此静止场景回退不能由 IDEA 浮窗解释。
