# 反馈调度与 X11 读回：修复、对照和部署

本轮已修复并部署通用的事件就绪与视频反馈处理问题，**没有达到延迟减半**。
在相同 1×、30 FPS 上限下，交错对照各 240 条：端到端 P50 为
**144.876 → 142.487 ms**，P95 为 **220.460 → 203.589 ms**。
中位数只差 2.388 ms，不能据此宣称稳定的大幅提速；尾部这轮有所下降。

[统计、最慢五条与两端独立时间线](2026-10-27-scheduler-feedback.json)、
[脱敏原始记录](2026-10-27-scheduler-feedback.raw.jsonl.gz)保留全部正式轮次和诊断，
也保留只修事件处理、尚未修反馈队列时没有获得收益的试验。

## 条件与边界

- Mac → `10.0.1.66`，仍经 `utun4`，小包 RTT 约 20 ms；未更换拥塞控制或放宽安全设置。
- 输出 1470×809、1×、H.264、协商上限 30 FPS，编码质量和 GOP 未改。
  X11 自有 GTK 夹具保留 2940×1618 的 2× 源 backing，接收端为 1×；每 33 ms 更新一小块动画。
  原生 Wayland 烟测使用 1× 源。这不是修改用户应用的缩放或清晰度来换延迟。
- Mac 接收区为 1445×793 点、60 Hz。起点是 SurfaceView 输入函数，终点是 renderer 返回对应显示缓冲可用。
  **不含外设、屏幕扫描和面板响应，不是 input-to-photon。**
- 正式对照用未插桩 Agent、原网络程序；不同时编译或运行门禁。
  顺序为旧、新、新、旧、新、旧、旧、新；每轮按键、点击各预热 2 次、正式各 30 次。
  旧版 Agent 核心等同已安装的 `c0d6d74`，新版核心为 `349d2c2`。
- 比较阶段使用独立 Agent/配对状态和同一网络程序；真实用户应用保持运行。
  生产安装后的单实例测量另列，避免把两种运行条件混在一起。
- Ubuntu 当时仍运行其他用户任务，负载约 3–5，读回和输入耗时有波动；没有停止这些任务。
  本轮不能与较早的 69.4 ms 或上一轮 73.6 ms 直接相减作为代码收益。

## 修复内容

1. `8e80b1a`：X11 在阻塞等待 fd 前，检查 x11rb 内部是否已有事件。
   使用保留顺序的单事件 peek，避免同步 reply 已把事件读入库缓冲后，主循环仍睡眠。
   事件继续交给原有 FIFO/剪贴板处理，不消耗或越过选择事件。
2. 同一提交：记录 DamageSubtract 的完整请求序号，忽略已被快照覆盖、但仍留在队列里的旧 Damage。
   保留相等及更新序号的通知，包括 16 位序号回绕后的真实新绘制；采集失败仍重新标脏。
   旧实现已在实际 Xvfb 回归中复现失败，新实现通过。
3. `349d2c2`：视频显示反馈在请求读取线程到达后直接更新共享 QoS，避免等待同步采集和窗口维护。
   键鼠、焦点、文本、尺寸等请求仍走原来有界 FIFO，首条请求仍必须经过 hello 校验。
   不修改帧率上限、退避阈值、编码质量或传输协议。

这些处理按事件和协议类型工作，没有 IDEA、ChatGPT 或其他应用名分支。

## 找到的反馈排队

在独立诊断中，反馈已经到达 Agent，却仍在主循环队列等待。它原本被计入显示反馈延迟，
因此可能把 Agent 自己的工作拥堵当作客户端/传输压力并降帧。

| 到达 → QoS 处理 | 修复前（245 次） | 修复后（260 次） |
|---|---:|---:|
| P50 | 17.904 ms | 0.0176 ms |
| P95 | 81.808 ms | 0.0324 ms |
| 最大值 | 122.916 ms | 0.0564 ms |
| excess 超过 100 ms | 11 次 | 0 次 |

这轮修复前有 68 次反馈对应 22 FPS 目标、16 次对应 27 FPS，其余为 30；修复后记录中均为 30。
**这是局部排队修复的证据，不等于省下同样多的端到端延迟。**
两轮诊断各 40 条的端到端中位数反而为 142.923 / 188.539 ms，读回耗时也不同，
所以未将它们当作性能提升对照；正式比较使用下面的未插桩交错测试。
诊断仍有日志与埋点成本，其绝对值不替代正式结果。

## 剩余瓶颈：同步 X11 读回

额外诊断为采集内部增加墙钟和当前线程 CPU 检查点，共 320 次，不录制像素。

| 检查点 | 墙钟 P50 / P95 | 线程 CPU P50 / P95 |
|---|---:|---:|
| 窗口归属校验 | 0.082 / 0.567 ms | 0.051 / 0.111 ms |
| Damage 确认 | 0.019 / 0.055 ms | 0.010 / 0.022 ms |
| 命名窗口 pixmap | 0.013 / 0.032 ms | 0.007 / 0.016 ms |
| 缩放请求与检查 | 0.077 / 0.163 ms | 0.020 / 0.042 ms |
| SHM 读回并复制快照 | **26.350 / 51.886 ms** | **0.780 / 1.418 ms** |
| 读回后的格式元数据 | 0.011 / 0.020 ms | 0.009 / 0.017 ms |

等待主要在 X 服务完成 GetImage；Agent 自身计算/复制不是这 26 ms 的主要部分。
这尚不能唯一分辨 X 服务调度、图形驱动同步或其他外部等待，不能全命名为 GPU 耗时。
采集仍与控制主循环串行，因此也会推迟新输入；本次反馈旁路没有把像素读回变成异步。

下一处值得改的是非阻塞采集与输入分离，并验证帧的新旧、几何版本、Damage 重新激活和缓冲区所有权。
不能只把同一连接上的同步调用搬到线程，就宣称输入已不受 X 服务读回阻塞。
不应优先继续省小于 0.1 ms 的窗口校验，也不能把服务端仍可写的 SHM 直接借给编码器。

可复现诊断入口：

```sh
python3 tests/performance/agent_stage_probe.py /absolute/new/archive \
  --isolated-state --trace-only --x11-capture-stages
```

该命令只生成测试源码副本；产物需配置私有状态/日志，不能安装成正式 Agent。
`0b1fd56` 同时把诊断 JSON 预先序列化后整条写出，减少逐字段写文件的观测干扰；
它没有单独解决本轮高端到端耗时，不算生产速度优化。
