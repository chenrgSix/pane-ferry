## 本机真实 GPU 路径的采集到发布耗时

修复了上一轮私有 GNOME 夹具只有首帧的问题：启动概览遮住测试窗口，GTK/Present 停止持续重绘。
现在仅向临时复制的扩展加入测试操作，隐藏私有合成器的概览、激活自有窗口，再按正常协议调整到目标尺寸。
正式扩展和当前用户桌面没有改动。

环境为本机 Ubuntu 26.04.1、GNOME 50.1、i5-13400 / UHD 730；独立 GNOME、XWayland 和自有 GTK 滚动窗口。
2940×1618、60 FPS 上限、关闭视频反馈；每轮预热 2 秒后测 8 秒，软编、硬编、硬编、软编交错运行。
采样期间没有并行编译或运行其他基准，用户的日常工作负载保持运行。
最终发布帧全部由日志确认走 `linear` / DRI3 读回，而非 Xvfb / MIT-SHM。

当前软件实现两轮共 679 帧，测得：

| 同一帧的阶段 | P50 | P95 |
| --- | ---: | ---: |
| 开始读取像素 → 不可变快照完成 | 14.68 ms | 24.40 ms |
| 颜色转换及 H.264 编码调用 | 15.84 ms | 21.15 ms |
| 快照完成 → 完整帧写出 | **21.06 ms** | **31.62 ms** |
| 开始读取像素 → 完整帧写出 | **36.01 ms** | **50.95 ms** |

这里的发布终点是完整 H.264 JSON 行写入本机 Unix socket，不含 QUIC、客户端解码或最终显示。
起点是读回函数入口，不含此前应用绘制和等待采样；各行分位数不能相加。
全部样本核对原有消息 seq、唯一 capture ID、消息字节数和阶段时间顺序，未缺失关联。
插桩存在开销，只统计最终发布帧；这不是生产绝对时延保证或真实应用验收。

此前 Xvfb 的 28.40 / 49.41 ms 来自另一条采集路径与另一轮负载，不能用来推断本轮代码变慢。
本轮没有重新部署或改变正式编码实现。

## 未采用：更多 CPU 线程

临时候选把大窗口转换线程上限从 4 提到 6，并把 ≥4M 像素的 x264 slice 线程从 4 提到 6。
仍满足 I420 两行色度边界；9 项显式 GStreamer 回归通过。
私有 Xvfb、相同尺寸和帧率上限的完整滚动对照为：

| 指标 | 当前实现 | 6 线程候选 |
| --- | ---: | ---: |
| 发布帧率 | 36.94 FPS | 37.06 FPS |
| 帧间隔 P95 | 63.68 ms | 63.29 ms |
| Agent CPU，单核等效 | 169.05% | 189.42% |

逐轮发布 FPS 为 36.63、37.38、36.75、37.25。
增加线程没有得到实质吞吐收益，CPU 消耗反而增加，因此未保留产品改动。

## 未采用：Intel 核显 H.264

机器有 UHD 730，但系统缺少 Intel VA 视频驱动，原 GStreamer VA 插件注册 0 个功能。
将 Ubuntu universe 的 `intel-media-va-driver 26.1.2+dfsg1-1` 和 `libigdgmm12 22.9.0+ds1-1`
下载、解包到 `/tmp`，仅给测试子进程设置驱动目录、库路径和独立 GStreamer registry；随后可以使用 `vah264lpenc`。
没有安装系统软件，也没有向正式服务添加环境变量。

第一版直接 GPU BGRx → NV12 转换没有通过现有解码画质对照：奇数几何出现明显失真，
限制为对齐尺寸后，大窗口 MSE 仍从参考的约 215.6 增加到约 235.7。
这些失败均保留，未将该转换用于后续性能候选。

随后保留原 CPU I420 颜色转换，测试 VA 后处理转 NV12，再交给低功耗 H.264 编码器。
使用原码率、QP 上限 28、相同 GOP、无 B 帧、1 个参考帧；`target-usage=4`。
该版本通过现有三帧解码画质和输入租约释放检查，但性能收益没有覆盖真实 GPU 路径：

| 同轮对照 | 当前软编 | VA 后处理 + 硬编 |
| --- | ---: | ---: |
| Xvfb 发布帧率 | 38.13 FPS | 39.69 FPS |
| Xvfb Agent CPU，单核等效 | 169.67% | 82.42% |
| GNOME/XWayland 发布帧率 | **42.44 FPS** | **36.38 FPS** |
| GNOME/XWayland 转换及编码 P50 / P95 | **15.84 / 21.15 ms** | **21.98 / 31.52 ms** |
| GNOME/XWayland 采集完成 → 写出 P50 / P95 | **21.06 / 31.62 ms** | **31.12 / 46.39 ms** |
| GNOME/XWayland 开始采集 → 写出 P50 / P95 | **36.01 / 50.95 ms** | **50.35 / 68.81 ms** |

Xvfb CPU 下降约一半值得记录，但不能据此认定实际桌面更跟手。
GNOME/XWayland 四轮软编/硬编/硬编/软编 FPS 为 41.88、36.25、36.50、43.00；
源端绘制分别为 54.38、61.88、60.88、54.25 FPS，硬编没有因源窗口缺少重绘而吃亏。
具体额外开销是否来自上传、GPU 资源竞争或驱动执行，需要更细的 GPU 诊断；本数据不能唯一归因。

另测 CPU I420 → NV12 后直接上传给硬编，省掉 `vapostproc`。
画质检查通过，但编码调用中位数仍约 21.34 ms，软编约 14.97 ms，没有缩短该区间。
四轮 FPS 为 46.50、42.75、17.63、17.50；后半段两版都明显降速，全部保留，不能挑选前两轮作为稳定收益或给背景负载指定唯一原因。

原生 Wayland/PipeWire 另做探索性吞吐检查，软编/硬编/硬编/软编为 30.88、30.50、31.63、36.38 FPS，
源端重绘频率也随之变化，没有得到硬编吞吐改善的证据。
该探索使用正式软编二进制与带 X11 阶段钩子的硬编候选，且探针没有原生采集时间戳；
不能据此声称精确的原生编码性能差异或采集到发布延迟。

所有硬编源码只存在于临时副本，含实验性的自动选择和回退逻辑，没有合并或部署。
当前证据不支持为了滚动流畅度启用它。
