# 显示完成后及时返回视频额度

Mac 更新至 `9ead41a` 后的真实 4:4:4、60 fps 复现已收到分段计时。
一个前台播放的 2 秒统计区间中：

| 阶段 | P50 | P95 |
| --- | ---: | ---: |
| Windows 采集、合成和编码 | 2.63 ms | 3.05 ms |
| Mac 解码 | 1.44 ms | 2.56 ms |
| Mac 解码完成至显示提交 | 0.13 ms | 0.92 ms |
| 显示提交后等待发送反馈 | 14.63 ms | 45.85 ms |
| 传输、桥接及反馈返程残余 | 28.28 ms | 168.34 ms |
| 发送端等待六帧额度释放 | 16.34 ms | 132.38 ms |

各行分位数来自独立样本集合，不能直接相加。残余不是纯网络 RTT，也不能仅据此认定丢包。
活动状态改变仍有约 210 ms 编码器重建，但这不能解释持续前台播放时所有停顿。

旧 Mac 在显示完成后仍每 50 ms 批量确认一次，并等待下一次 pump。
六帧额度在 60 fps 下只有约 100 ms 余量，这段人为等待使正常抖动也更容易暂停采集。
现在直接在原有显示提交回调中发送累计确认，突发回调按最多 120 次/秒合并，
pump 负责补发最后一个暂缓的确认，避免静止画面留下未确认帧。
仍然在显示提交后才确认；不提前确认尚未解码/提交的帧，也不扩大在途帧上限。
原有协议及可选计时能力协商不变，不要求特定 GPU。

Mac 回归覆盖正常 60 fps 的每帧反馈、突发合并、末帧确认，以及从 receive 到显示回调
再到反馈消息的完整本地计时传递。真实网络尖峰仍需进一步测量和用户复测，
不能将此改动表述为已解决全部周期性卡顿。
