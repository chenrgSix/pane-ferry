# 80 条旁路样本中端到端最慢的 5 条原始时间线

材料仅提取既有历史记录：`observation-round2-trace` 与 `observation-round5-trace` 各 40 个正式响应，排除预热。
条件：`10.0.1.66`、1×、30 FPS、Agent `bda43cf`；按 Mac `draw_end - start` 降序取前 5。
这 80 条旁路样本的中位数为 95.895 ms、P95 为 131.702 ms；不是另 240 条无插桩正式对照的 93.063 ms。

原始纳秒时间、两个时钟域的逐事件时间线、完整关联字段及 80 条排序索引见[配套 JSON](2026-10-26-overlay-slowest-five.json)。

## ID 与测量边界

- 输入关联 ID 为 `run/input-count`；`count` 是原始日志的视觉计数，组合标签由本材料生成，并非协议自带的输入 ID。下表 `R2`、`R5` 分别指两轮 trace。
- I420 ID 是捕获样本身份；RWP ID 是编码后实际写出的 `frame_id`，两个编号空间不能混用。原始帧身份另保存在 JSON 的 `endpoint_raw_id`。
- “首个响应”严格指主循环第一次 pull 到视觉计数匹配的 I420。3 条可通过首读时间落在最终单次 capture 调用内回溯确认；另 2 条首读时间早于最终 capture，原 ID 未记录，留空。它们的首个已记录发布帧仍可明确给出。
- 没有逐次 producer-ready 日志，不能确认任何一条的“生产者绝对最早完成响应帧”。不得从 ID 连号猜补缺失值。
- “终点帧”指 Mac 匹配到并结束端到端计时的那一帧；该输入后还可能有同计数动画帧继续发布。5 条的首个实际写出响应帧恰好就是终点帧。
- Mac 以本次输入处理开始为 0，Linux 以 Agent 读到输入为 0，不能将两个轴的相同相对数值视为同时发生。终点是 renderer 缓冲身份匹配，不是面板扫描。

## 同机差值可精确闭合的耗时项

混合段为 `(Mac 回显收到 − Mac 写入结束) − (Linux 写出结束 − Agent 收到输入)`。它是残差，包含上下行、桥接和序列化，无法放在 Linux 时间线的某一个单独位置；也不能进一步拆成精确单向网络延迟。

## 对下一步判断的支持程度

- 混合段在全部 80 条中的中位数 31.513 ms、P95 35.522 ms；3/80 超过 40 ms。本次最慢第 3 条为 56.741 ms，不能把混合成本视为完全恒定。单独 ICMP 往返约 19.5 ms，剩余部分尚未拆清。
- `publish − max(eligible, 最终样本 ready)` 在全部 80 条中：中位数 1.068 ms、P95 8.980 ms、最大 15.935 ms；4/80 至少 10 ms，0/80 达到完整的 33.333 ms。发布时已有更新完成响应却仍选旧帧的标记，在这组记录为 0。
- 上述 0/80 只描述最终这一次发布相对当前允许时刻的延后，不能单独排除更早机会曾被错过；尤其第 2、3 条的首次响应帧 ID 缺失，无法完整回溯首次 ready。
- 对尾部而言，已有明确的验证目标是发布前维护跨截止：最慢第 2、3 条分别出现 15.935、11.042 ms 迟到。它们值得单独做保持 30 FPS 的对照，但不能把正常的 28–32 ms 节拍等待也算成可消除开销。
- 对整体中位数而言，混合段持续约 31.5 ms 覆盖面更广；应先进一步拆分它，再估计可减少多少。不能仅由这 5 个最慢样本估算全局收益，也不能断言“已就绪帧额外多等完整一轮”已得到证明。
- 这份材料暴露的测量缺口是未保存每个 ready/first-matched 的完整帧身份。后续若验证漏选或错过前一机会，应在发生时记录输入关联 ID、I420/raw ID、ready 时间和被替换/丢弃原因；本次没有修改或重跑生产程序来替代这 80 条历史数据。

提取校验：80 条唯一输入、每轮 40 条；端到端排序、帧编号与视觉计数、RWP 写出对应、时钟域、原始记录字段和差值闭合均已检查。
