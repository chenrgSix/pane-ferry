# 远端采集与编码优化后的延迟

2026-10-21，Apple Silicon Mac / Ubuntu 26.04.1，同一 `10.0.1.66` SSH 路径（utun4）。
本轮重新构建并测量旧版 `30309a3` 与优化版 `31db3a5`，不直接拿先前另一时段的数字做前后比较。
高清场景的整体中位数降低约 29%–37%，动态场景的尾延迟仍有波动。

## 改动及画质约束

- MIT-SHM 1.2 通过同一认证 X11 连接取得私有 fd，减少整帧 socket 传输；只读映射复制成独立快照，避免后续采集修改正在编码的像素。不支持或失败时保留 socket GetImage。
- 系统 GStreamer C API 直接接收只读像素的 Arc 租约，移除原始帧的 Python 子进程传输、拼接和 GstBuffer 再次填充。停止管线后释放租约。
- XDamage 只订阅已授权可见窗口，由重绘和输入就绪唤醒；元数据检查与采集时钟分离，静止窗口跳过重复读图。保留最短 33ms 采样间隔、扩展不可用时的轮询、尺寸变更及重连首次快照。

像素宽高、界面缩放、BGRx→I420 颜色转换、OpenH264 screen/low 配置、码率公式
`clamp(width*height*3, 2_000_000, 24_000_000)`、GOP 60、四线程编码、QP 上限 28、禁止编码器跳帧均保持原设置。
时间戳保留原 sequence/30 规则。没有降低分辨率、色彩采样格式或码率来换取本轮数字。

在相同原始输入上，对 640×480、641×483、2940×1612 各三帧（关键帧及连续 P 帧）运行新旧编码器，
九帧解码后的 RGB 像素均完全相同；还核验原始输入没有被修改、管线关闭后租约已释放。
共享内存和 socket 捕获在调整尺寸前后逐字节一致，失败回退通过。
这些是指定夹具的画质回归证据，不代表所有应用、画面或驱动都经过逐像素验收；产品仍是原有有损 4:2:0 视频。

## 全链路结果

每次运行方向键、文字提交、点击各 30 次，共 90 个有效样本，另排除各两次预热。
共八次运行、**720 个有效样本**，48 个预热样本未计入统计。全部有效帧通过对应输入标记、尺寸、H.264 和实际硬件解码校验。
起点为产品 SurfaceView 输入处理函数，终点为 Mac 实际 AppKit 绘制完成；不含键盘硬件、拼音组合时间、系统最终合成与物理面板响应。
使用独立 Agent/HOME/Xvfb/GTK 夹具，测量期间不接管现有 Firefox 或 ChatGPT。

以下单位均为 ms。2560×1664 持续更新汇总包含两轮的全部样本，每版 180 个；其他场景每版 90 个。

| 场景 | 旧版中位数 | 新版中位数 | 旧版 P95 | 新版 P95 |
| --- | ---: | ---: | ---: | ---: |
| 2940×1612 持续更新 | 163.04 | 115.37 | 218.65 | 180.25 |
| 2560×1664 持续更新，两轮合并 | 141.46 | 100.21 | 226.44 | 244.75 |
| 2560×1664 静止后输入 | 125.56 | 79.72 | 254.17 | 111.10 |

2560×1664 持续更新的首轮波动较大，整体中位数几乎没有改善；因此倒序再测一次，完整保留首轮，未筛选快速样本。

| 独立轮次 | 运行顺序 | 旧版中位数 / P95 | 新版中位数 / P95 |
| --- | --- | ---: | ---: |
| 2560×1664 持续更新，首轮 | 旧→新 | 156.59 / 255.91 | 156.43 / 276.35 |
| 2560×1664 持续更新，复测 | 新→旧 | 133.13 / 209.88 | 89.49 / 116.94 |

后台应用和网络负载没有固定，不能把每一项前后变化都归因于此次代码。
两轮之间的波动也说明本结果不是帧率或尾延迟保证，不能承诺每次操作都在 100ms 内完成。

## 具体减少了哪些开销

2940×1612 持续更新组的以下**平均**阶段耗时可加总回总平均值；分阶段中位数不应相加。

| 阶段 | 旧版平均 ms | 新版平均 ms |
| --- | ---: | ---: |
| 两端输入内部处理 | 5.72 | 3.47 |
| 应用响应到采集完成 | 45.88 | 30.48 |
| 等待编码、编码与回包准备 | 63.19 | 33.29 |
| SSH / 网络 / 读取缓冲剩余段 | 27.49 | 40.71 |
| Mac 解码到绘制完成 | 22.70 | 19.76 |
| 总平均值 | 164.98 | 127.71 |

远端画面产出的两段合计从 109.07ms 降到 63.77ms，约减少 42%。
进一步诊断中，实际捕获调用的中位数为 9.96→4.64ms，编码通路为 44.17→29.11ms，等待编码为 14.26→0.02ms。
2560×1664 静止组的应用响应到采集完成平均为 31.80→13.49ms，等待编码及编码为 39.40→25.97ms。

偶发长停顿仍在：新版 2940 组最大值 667.71ms，其中 581.91ms 落在 SSH/网络/读取缓冲剩余段，
对应 8705 字节普通视频包；旧版静止组也出现过 1117.95ms，其中该段为 1037.02ms。
不能把它解释为单纯编码慢或关键帧过大。此处是往返总耗时扣除两端内部时间得到的剩余段，
不相减未经同步的跨机时钟，也尚未拆分 TCP、SSH 复用、读端缓冲各自的贡献。
