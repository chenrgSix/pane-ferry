# Windows 4:4:4 关键帧闪烁

用户确认 e6c6ccd 已明显改善流畅度，但出现黑闪/色块，且同场景 4:2:0 正常、
4:4:4 闪烁。稳定播放日志中没有频繁编码器重建或恢复请求；约 60 fps，
Mac 解码队列中位数约 7 µs。不能因此认定显示正确。

## 本机隔离

使用自有 `tests/fixtures/windows-video.ps1` 动画，客户端尺寸请求 2560×1400，
实际发布 2562×1432、载体 4096×1792，通过本机 IPC 保存编码流。
没有记录用户应用画面。FFmpeg 独立解码并按 `444-atlas-v1` 布局还原像素。

- 旧版 600 帧中 10 个关键帧，约每 60 帧一次。全部可解码，但第 60、300 帧的
  蓝条有明显块状杂色，灰度网格偏色、细节损坏；随后数帧恢复。
- 采样灰度网格区域（排除标题和顶部彩条）中，关键帧前色度离中性 128 的
  平均误差为 0.004–0.005，关键帧跃升到约 1.48。前后还原 RGB 的平均值
  从约 (195,195,195) 变为约 (193,188,190)。
- 旧版载体 UV 平面逐帧平均差最大约 2.96/2.64，峰值位于周期关键帧。
  这证实 Windows 输出已有可见色块/偏色；没有在合成夹具复现整幅纯黑，
  不能声称已证明用户所有黑闪都只有这一原因。
- 单独限制最大 QP 为 28 后，关键帧恢复到约 0.8–0.93 MB，仍每秒一次，
  会重新引入突发；因此没有单独部署这个中间方案。

## 实现

保持 CBR、短 HRD、无 B 帧，在编码开始前设置最大 QP 28，避免过度量化损伤
色度数据。同时将 GOP 设为标准接口允许的最大间隔 `u32::MAX`，使用启动和
显式恢复时的 IDR；这不是将每秒刷新改成每几秒刷新。`0` 表示驱动选择间隔，
不能用来表示禁用周期 IDR。编码器仍可能因内容变化产生额外关键帧。

QUIC 媒体按可靠有序流交付，接收端已有显式关键帧恢复请求；尺寸变化和需要
重建编码器的路径保留。硬件候选若不支持配置，仍沿初始化失败路径回退，
不绑定厂商，已实测系统软件编码器支持相同设置。

HRD 是码率预算而不是每帧字节硬上限。质量约束可以让首次连接、恢复、复杂
场景的帧超过预算，不能声称任何内容下都能保证小帧或固定延迟。

接口依据：[最大 QP](https://learn.microsoft.com/en-us/windows/win32/medfound/codecapi-avencvideomaxqp)、
[H.264 编码器与 GOP 范围](https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-encoder)。

## 对照结果及回归

同一夹具新版连续 1800 帧只有启动 IDR：平均 39.39 Mbps，帧大小 P99 126,447 B，
最大 929,769 B（启动帧）。没有每秒一次的大帧。交付间隔中位数 16.65 ms，
P99 27.79 ms；仍有非周期性调度波动，不宣称所有帧都达到 16.67 ms。

第 59/60/61、299/300/301 帧相同灰度区域的采样色度误差均为 0。
完整序列第 30 帧之后的载体 UV 逐帧平均差最大约 0.123/0.123，
独立解码没有错误。仍需用户在真实页面验收。

硬件直接纹理探针扩展为 180 帧，覆盖原来的两个自动 GOP 边界，要求只有
启动和第 120 帧的显式恢复产生关键帧；恢复沿用同一 MFT，并保存可独立解码的
恢复后缀。覆盖 320×180、1602×932、2560×1440 的 420 和 444。
软件 64×48 增加 125 帧无周期 IDR 检查，其他实际软件编码尺寸保留。
上述实际硬件/软件探针及 `scripts/check-windows.ps1` 均通过；FFmpeg 独立
解码 16 条测试流（包含恢复后缀）没有错误。

本机取证可设置 `PANEFERRY_CADENCE_EXPORT` 为 H.264 输出路径，
`PANEFERRY_CADENCE_FRAMES` 为 2–1800，运行 `local_cadence` 示例。
只选择固定标题的合成夹具。导出期间增加 base64 解码和内存复制，时序统计应
与非导出模式区分；单次导出内存上限 256 MiB，结束后才写磁盘。
