# Windows GPU 合成与全色度传输

本轮在 `00ca2ce` 基础上实现。保留单应用授权、窗口身份验证、源端弹窗合成及输入路由；不采集整个桌面，不绑定显卡厂商。

## GPU 路径

各 WGC 会话共用一个 D3D11 设备。采集帧先在显存复制到该表面的可复用纹理，再按已验证的窗口顺序和布局合成到 R32_UINT 画布。计算着色器使用与 CPU 相同的预乘 alpha 混合和整数 BT.601 转换，避免每个窗口各自回读、CPU 合成和 CPU 转换。

最终编码输入仍通过一次 staging buffer 回读到系统内存，再进入现有编码器。默认软件编码，可选系统硬件编码仍可使用；**尚不是纹理直接送硬编的全显存链路**。`gpu.compose_submit` 仅为命令提交耗时，GPU 的执行与等待包含在 `gpu.convert_readback` 中，不能用提交耗时冒充完整 GPU 执行时间。

默认尝试 GPU 合成；设备/着色器初始化失败或运行错误时清理表面缓存、重新建立软件合成路径。`PANEFERRY_VIDEO_GPU=off` 可强制 CPU 合成。核显满足 D3D11 能力也可使用，无独显要求。此开关不等于关闭 WGC 自身的图形设备需求。

## 4:4:4 色彩模式

Mac 启动器的“显示设置 → 接收色彩”新增“清晰色彩 · 4:4:4（试用）”，默认继续兼容 4:2:0。手动和自动接管均使用该偏好；保存后关闭旧接收窗口并重新接管。Windows 发布端声明 `video.color.444-atlas-v1` 能力后，新 Mac 才会请求这一模式。旧接收端继续接收原有 H.264 视频，不会收到打包图像。

系统 H.264 编码器没有通用的 High 4:4:4 输出，因此使用完整色度平面的显式打包协议。普通 NV12/H.264 是承载格式，并非原生 H.264 High 4:4:4 Profile。接收端还原的是逐像素 Y/U/V，无源色度降采样；编码仍然有损，不是 RGB 无损，也不是靠放大 4:2:0 声称得到 4:4:4。

### `444-atlas-v1` 布局

- 原始应用尺寸为 `width × height`；`w = width + width%2`，`h = height + height%2`。奇数右/下边缘复制最近像素，`N = w*h`。
- `encoded_width = min(2*w, 4096)`；`encoded_height = ceil(2*N/encoded_width)` 再向上补成偶数。编码尺寸各不超过 4096，总面积不超过 16,000,000。
- 载体 Y 平面按连续字节编号：`[0,N)` 保存完整 Y；`[N,2N)` 保存完整 U。载体 UV 平面的前 N 个字节保存完整 V。其余填充字节为 128。
- 原像素色彩使用有限范围 BT.601，与兼容路径相同；U/V 按每个像素计算，不做 2×2 平均。
- `video.enable` 仍使用 `codec: "h264"`，额外带 `color: "444-atlas-v1"`。`video.ready` 和每个 `frame` 返回实际 `color`。缺省为 `"420"`；未知名称拒绝。一个编码流中不改变打包模式。
- `width/height` 始终是应用逻辑像素尺寸，输入坐标和窗口布局不使用载体尺寸。Mac 在分配解码资源之前按模式重新计算并严格核对 `encoded_width/encoded_height`，总解码预算计入载体面积。
- Mac 用 VideoToolbox 解码为原始 NV12 平面，再用 Metal 还原到 BGRA。Metal 不可用或失败时使用 CPU 还原；两者都不会将承载图像当普通 YUV 颜色直接显示。

使用单一 H.264 流保留现有帧序、关键帧恢复、流控和网络二进制封装；没有两个编码流失去同步的问题。代价是编码像素量约翻倍、更多解码/还原工作和带宽。本模式保持明确可选，不以降低源尺寸抵消开销。

## 本机验证与边界

- D3D11 合成及兼容/全色度转换对照 CPU：奇数边缘、负坐标、透明和半透明层、重复覆盖，逐字节一致。
- 真实 GPU 菜单和模态弹窗测试通过：画面包含弹窗，扩展/收缩画布及点击/文本输入正常。
- GPU 采集线程在真实动态窗口输出 120 帧，4:4:4 编码视频经 FFmpeg 独立解码 120 帧无错误、无 B 帧。
- 最大化/还原及 60/1/5 fps 六次切换通过。强制 CPU 合成和软件编码时也能输出 4:4:4；在测试中最大化后的 2560×1392 窗口输出 120 帧约 2.963 秒，不能承诺软件全色度始终达到 60 fps。
- 系统软件编码器已验证 64×48、1602×932、2560×1440、4096×1900 的原始全色度图像。MFT 的最大输出工作区与实际网络包上限分开约束；实际包仍不超过 12 MiB。
- 合成的 64×48 单像素红蓝相间样本独立解码后，Y/U/V 平均绝对误差约 1.19、最大 5（8 位数值）。该样本还在 macOS 15 CI 上经 VideoToolbox 和接收端还原，验证红蓝细线；不是任意应用的综合画质测量。

同一 1602×932 动态测试窗口，局部 IPC 各读取 240 帧，软件编码：

| 指标 | GPU + 4:2:0 | GPU + 全色度 |
| --- | --- | --- |
| 本地交付率 | 60.27 fps | 60.25 fps |
| 帧间隔 P50 / P95 / P99 | 16.71 / 19.00 / 24.09 ms | 16.65 / 18.98 / 22.12 ms |
| 测试内容码率 | 3.49 Mbps | 6.63 Mbps |
| 转换及回读 P50 / P95 | 0.485 / 0.707 ms | 0.828 / 1.053 ms |
| 编码 P50 / P95 | 1.640 / 2.196 ms | 3.059 / 3.998 ms |
| 单次采集到编码调用 P50 / P95 | 2.806 / 3.420 ms | 4.465 / 5.529 ms |

计时区间有正常的无帧调用；交付率不等于不同源图像数量。上述没有包含真实 EasyTier→Mac 链路及物理上屏延迟，也不能替代用户设备上的流畅度和画质验收。上一轮 CPU 合成测试的同类单次处理 P50 约 4.10 ms，仅作为顺序测试参考。

Mac CI 已迁移至 macOS 15，原 macOS 14 runner 正处于官方退役停机窗口。独立接收端检查先于较慢的全项目门禁执行，以直接验证 Windows 编码样本与 Mac 解码互通。
