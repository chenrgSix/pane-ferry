# Ubuntu 本机滚动吞吐：大窗口 RGB 转换

2026-10-28，在本机 Ubuntu 26.04.1 / GNOME 50.1、i5-13400 / Intel UHD 730 上，
保留大窗口 X11/XWayland 编码输入的有界并行颜色转换。最终构建已安装到本机 Agent。
原生 Wayland 的并行裁剪转换候选没有通过完整采集吞吐对照，已撤回。

最终二进制在私有 Xvfb、2940×1618、60 FPS 协商上限下，连续滚动发布吞吐
**40.19 → 46.75 FPS，增加 16.3%**；P95 帧间隔 **41.50 → 38.15 ms**。
这是发布端到本机 socket 的测量，**没有测量 Mac 显示帧率或 QUIC 端到端效果**，也未达到稳定 60 FPS。

[机器可读统计、二进制与部署信息](2026-10-28-local-scroll.json)、
[完整逐帧数据、探索基准与测试日志](2026-10-28-local-scroll.raw.json.gz)。

## 最终保留的改动

- 约 2M 像素起的 BGRx 编码输入，按可用 CPU 选择最多 4 个转换线程；小窗口保持单线程。
- 按实际转换行数选择 I420 两行色度边界对齐的分块；无法对齐则使用单线程。
  RGB 奇数高度先由原有补边管线补为偶数，再选择转换线程。
- 源分辨率、缩放、H.264 码率、QP、GOP、编码器线程和帧率协商策略保留。
  原生 I420 输入继续绕过 RGB 转换；最终原生 Wayland 捕获和裁剪管线与基线一致。

分块方式核对了 [GStreamer 1.28.2 转换实现](https://github.com/GStreamer/gstreamer/blob/1.28.2/subprojects/gst-plugins-base/gst-libs/gst/video/video-converter.c)。
回归测试另将实际 I420 有效像素逐字节与单线程版本比较，包含小窗口、1080p、奇数宽高、
2940×1618、8M 像素和缩放兼容路径；并核对源缓冲释放。

本轮目的是改善连续重绘吞吐。此前 1470×809 的并行转换没有降低点击延迟，
见[10/27 预处理试验](2026-10-27-video-preprocessing.md)；本次没有把该失败结论改写为成功，
也没有给同样的小窗口开启多线程。

旧、新、新、旧各运行 8 秒，另预热 2 秒。使用相同自有 GTK 滚动文档，源端实际绘制均约 60 FPS；
按完整 H.264 JSON 行收到时刻统计，不包含解码与显示。正式采样期间没有并行编译或运行其他基准。

## 保留的探索与未采用方案

早期候选同时修改 RGB 编码输入和原生裁剪转换。Xvfb 不经过后者，8 轮 2940×1618 对照为
45.78 → 49.47 FPS（约 +8.1%），P95 32.33 → 33.15 ms，尾部没有改善。
这与最终复测分开保存；不能拼接两次基线，或把机器负载变化算作代码收益。
1470×809 控制组为 57.06 → 57.31 FPS，基本相同。

4000×2000 探索组两版均只有约 4.81 FPS，源绘制也未稳定在 60 FPS；该场景没有得到吞吐收益，
没有因转换微基准变快就宣称 8M 画面已能稳定 60 FPS。

原生 Wayland 使用独立 GNOME、RecordMonitor/PipeWire 应用场景，同样测试 2940×1618、1×、60 FPS 上限。
旧、新、新、旧四轮为：

| 版本 | 发布 FPS | 源绘制 FPS |
| --- | ---: | ---: |
| 基线 | 42.63 | 42.63 |
| 原生并行候选 | 40.63 | 40.50 |
| 原生并行候选 | 40.38 | 40.38 |
| 基线 | 41.13 | 41.38 |

原生并行候选平均 40.50 FPS，低于基线 41.88 FPS。单独转换微基准虽有收益，完整采集没有受益，故撤回。
初始奇数裁剪高度的像素对照失败，以及首次测试窗口装饰导致绘制尺寸不匹配，均记录为准备失败；
修正后才运行上述对照，没有混入统计。最终构建不包含这项原生改动。

## 补测：同一帧的采集到本机写出耗时

响应“采集到发布耗时”的补测，使用临时插桩构建，不替换正式 Agent。
仍为 **2940×1618、60 FPS 上限、连续滚动、私有 Xvfb/MIT-SHM**。
旧、新、新、旧各测 8 秒，另预热 2 秒；基线 659 帧、当前实现 714 帧，共 1373 帧。

这里的终点是 **完整 H.264 帧 JSON 行写入本机 Unix socket**，没有经过 QUIC。
起点是读像素函数入口，已完成工作线程最初的所有者检查；不含此前等待采样或应用重绘，也不含控制端解码和显示。
“采集完成”表示不可变像素快照已得到；内部 raw-frame `publish` 只是编码队列入口，不能冒充编码帧已经发出。

| 当前版本区间 | P50 | P95 |
| --- | ---: | ---: |
| 读取像素、准备快照 | 9.30 ms | 18.33 ms |
| 快照完成 → raw-frame 编码队列入口 | 0.09 ms | 15.03 ms |
| 等待编码工作线程 | 0.04 ms | 9.86 ms |
| 颜色转换及 H.264 编码调用 | 15.33 ms | 22.41 ms |
| 采集完成 → 完整帧本机写出 | **17.59 ms** | **34.55 ms** |
| 开始读像素 → 完整帧本机写出 | **28.40 ms** | **49.41 ms** |

各行是独立分位数，不能相加。完整细分还包括编码准备、base64/输出队列、JSON 序列化与 socket 写入，见 JSON。
当前版本整体最大值 175.50 ms，仍有长停顿。
同轮基线“开始读像素 → 本机写出”P50 / P95 为 **39.55 / 64.07 ms**，
“采集完成 → 本机写出”为 **29.49 / 49.23 ms**。这些是有插桩的阶段诊断，不与上一节未插桩帧率混算收益。

读回分配唯一 capture ID，沿不可变图像租约关联到编码工作，再随内部元数据传到写出线程；
在序列化前移除该元数据，业务协议不增加字段。接收端用原有消息 seq 与日志逐帧匹配，全部样本匹配成功、
capture ID 无重复、阶段时间单调。全程使用同一主机 CLOCK_MONOTONIC，不作跨机绝对时钟相减。
仅统计最终发布的帧，不为中途丢弃的快照伪造写出时刻。插桩也可能扰动调度，不能视为生产精确时延保证。

私有 GNOME/XWayland 预检实际进入 linear/DRI3 路径，但测试窗口随后停止重绘，只有首帧；
调整夹具启动尺寸、定时重绘与私有输出消费者后仍未取得有效连续样本。
这些失败单独保留，未将首帧或静止画面计入本节滚动结果；本节没有给出真实 GNOME/XWayland 连续采集到发布的数字。
