# Windows 合成路径第二轮优化

基于 `e9a4038`，保持应用主窗口、弹窗、菜单在 Windows 合成为同一条视频流。此次仅修改 Windows 后端，不修改协议、Mac 接收端、码率、分辨率或编码器选择。

## 改动

- x86_64 使用基线 SSE2 对预乘 BGRA 做四像素并行混合。不透明块直接复制；透明和半透明像素保留原来的舍入、饱和与跳过规则。其他架构保留标量路径，不增加 GPU 要求。
- 底层窗口完全覆盖原尺寸画布时，把背景初始化与首层混合合并为一次遍历，避免先清空整幅图再覆盖。缩放、多窗口扩展画布及空隙继续使用完整背景初始化。
- 没有新像素且布局未变化时，质量刷新/强制关键帧可复用回收的已合成图像；编码仍照常进行。窗口顺序、位置、尺寸和可见表面改变会使缓存失效。
- 某层已经更新、但后续弹窗尚未就绪而提前返回时，保留像素变化标记，避免下次误用旧合成缓存。
- 诊断分位数统一使用 nearest-rank，修复两条样本时 P50 可能高于 P95 的问题。

## 本机对照

默认软件编码；CPU 合成基准为 release 构建，每种场景预热 20 次、记录 120 次。弹窗基准为 800×600 半透明层，包含实际混合计算。

| 2560×1440 CPU 合成 | 修改前 P50 / P95 | 修改后 P50 / P95 |
| --- | --- | --- |
| 单窗口 | 1.927 / 2.529 ms | 0.493 / 0.622 ms |
| 窗口加半透明弹窗 | 2.826 / 3.475 ms | 0.729 / 0.921 ms |

部署前后使用同一个 1602×932 动态 WinForms 测试窗口，各读取 240 帧：

| 指标 | 修改前 | 修改后 |
| --- | --- | --- |
| 合成 P50 / P95（后一个完整计时区间） | 1.056 / 1.455 ms | 0.302 / 0.423 ms |
| 采集到编码单次处理 P50 / P95 | 4.898 / 5.914 ms | 4.097 / 5.033 ms |
| 本地交付速率 | 60.22 fps | 60.18 fps |
| 帧间隔 P50 / P95 / P99 | 16.76 / 20.70 / 23.89 ms | 16.68 / 21.59 / 23.05 ms |

CPU 合成耗时明确下降；本地帧间隔没有显示出明确改善。以上是单机顺序测试，受系统负载和 WGC 节奏影响，且前后诊断分位数算法有上述修正。`video.total` 包含未得到画面的调用，不代表远端上屏延迟。不能据此声称 Mac 端到端延迟下降同等比例，也不能将 60 fps 交付速率理解为每秒 60 张不同源图像。

## 验证

- 后端单元测试 11 项通过，发布端单元测试 6 项和真实配对 QUIC 集成测试通过。
- SIMD 对照标量：所有 alpha 值、非对齐切片、尾部、不透明块、随机颜色逐字节一致。
- 首层合成：负坐标、画布空隙、缩放、透明边缘与原先清背景再混合的结果一致。
- 真实菜单测试通过，包括菜单像素、点击、新窗口扩大画布、关闭后收缩。
- 真实模态弹窗测试通过，包括超出父窗口的画面、输入路由、关闭后恢复父窗口。
- 独立采集线程输出 120 帧并接受输入，约 2006 ms；FFmpeg 独立解码 120 帧无错误、无 B 帧。未测不同视觉帧数量。
- 六轮最大化/还原和 60/1/5 fps 切换通过，均产生新的流 ID 和关键帧。
- 已部署 Windows 发布端并确认 UDP 42424 监听，身份文件哈希未变。Mac 的真实网络/显示延迟仍待使用端验证。

复现 CPU 基准：

```text
cargo test --release --locked -p paneferry-backend-windows benchmark_native_scene_composition -- --ignored --nocapture
```

这一轮仍是 CPU 合成与软件编码优化，不是 GPU 纹理直送，也没有改变 NV12 / 4:2:0 的画质边界。
