# IDEA 远程延迟修复与验证（2026-10-24）

## 修改

- `bca2805`：PipeWire 单次只读映射，裁剪像素只复制一次；Wayland/桌面缓存与输出共享 Arc，消除整帧清零和第二次克隆，及时归还采集缓冲。
- `8ccade4`：待处理输入优先于采集，保留文本/按键/按钮边界；持续输入最多推迟维护 100 ms；完整窗口存活查询限为每 100 ms，仍保留进程身份和逐事件目标校验。
- `56a3e94`：优先 x264 ultrafast/zerolatency，同帧 slice 多线程，无 B 帧/lookahead；组件或首帧失败回退 OpenH264。保持尺寸、目标码率和 QP 上限。

## 已完成验证

- macOS `bash scripts/check.sh` 通过：格式、Rust 工作区测试、Python/JS 单元检查、前端测试与构建、Swift 构建、输入/剪贴板顺序、真实 QUIC/H.264 接收和重连检查。
- Ubuntu 26.04.1，i5-13400：Agent 27 项常规测试通过；4 项原生 GStreamer 测试显式执行通过（新帧唤醒、H.264 流、解码画质/像素租约、首帧失败回退）。Linux runtime、desktop authorization、desktop monitor 单元检查通过；release 构建通过。

更新后两轮采集样本 75/90、编码样本 65/82、反馈匹配样本 59/66。完整 GNOME RPC 调用由旧轮 3035 次减到 1283/1295 次。输入排队最大值由 201.864 ms 降到 46.027/31.841 ms。

改善在两轮都存在：采集中位数下降 56–60%，编码下降 61–64%，输入排队下降 64–72%。旧版基准包含重启前仍存活的独立应用，新版实测在它们结束后进行，因此这不是隔离所有后台负载的随机 A/B；分辨率、IDEA 进程、文档和滚动操作保持一致。

编码包更大是实际代价：捕获到的大块 socket 写入平均大小约 43.9 KB → 84.6 KB（旧轮→新版第 1 轮，阈值 >1024 B；不是纯 H.264 包大小），按一秒分桶的峰值约 3.78→5.60 Mbps。没有出现显著 socket 写阻塞，QUIC RTT 中位数保持约 5 ms。发送到解码反馈的中位数增加约 3.5 ms，P95 也上升；该项混合传输、客户端解码和最长约 50 ms 的反馈调度，不能当作纯传输延迟，也不能宣称传输阶段得到改善。

实测期间画面完整，尺寸保持不变，未出现编码回退、连接中断或新的 Agent 错误。静止时标题“近 2 秒未收到新画面”属于无变化不发送；滚动批次含大量间隔，标题 7–8 fps 不能代表持续运动吞吐上限。

## 后续断线恢复修复（同日）

后续异常中断时，Mac 网络进程仍存活，但对同一设备的路由请求排队且没有发出新的握手包；新建独立 QUIC 探针可以连到同一 Ubuntu。首次触发连接关闭的原因未被旧版本记录，不能倒推出是 IDEA、Agent 崩溃或多个窗口同时开启导致。

`7cd9ab4` 为每次连接建立设置覆盖排队、TLS、认证流和认证读写的统一 15 秒截止时间，关闭尚未注册的失败连接，并在本地调用方关闭时取消它的排队请求。`580d1cc` 增加有限大小、私有权限的网络故障日志，不记录业务请求、画面或剪贴板。Mac 部署后实际路由 hello 约 35 ms，设备恢复连接。

IDEA 复测还暴露了另一个画面阻塞：窗口资源缩放为 2×，Mutter 的 VideoCrop 持续报告 1470×809，而 CPU 合成的完整图像实际为 2940×1618。旧校验丢掉了所有新帧；仅重建采集流没有修复，按 1× 截取则会只显示左上角。这两个实验方案均未保留。`537029f` 对照当前逻辑窗口尺寸识别两种裁剪单位，校正范围后直接复制完整原始像素，并继续检查源 buffer 边界和拒绝其他过期尺寸。没有缩放图片，也没有改变输入坐标转换。

该行为与当前机器 Mutter 50.1 的 [窗口流裁剪路径](https://github.com/GNOME/mutter/blob/50.1/src/backends/meta-screen-cast-window-stream-src.c) 和 [窗口 CPU 合成路径](https://github.com/GNOME/mutter/blob/50.1/src/compositor/meta-window-actor.c) 相符；实机确认对象是当前 IDEA / README 预览，不代表所有桌面环境均已验收。
