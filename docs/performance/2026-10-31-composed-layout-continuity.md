# 合成窗口布局变化不再重启视频流

用户在 `8f30a08` 部署后仍反馈周期性卡顿。`c1a585b` 诊断版的实际 Mac 会话记录了多次 `keyframe_reason=geometry_race`，未出现队列丢帧或反馈超时重启。稳定采集编码通常约 3 ms；反馈延迟仍有尖峰，不能仅凭本机编码快就判断端到端流畅。

## 原因与修复

采集工作线程会先更新布局快照，再返回编码帧。发布端却用采集前的快照检查该帧，导致刚合成的新布局被误判过期、丢帧并强制新流。内部布局版本还被计入网络的几何版本，使接收端过滤旧帧；新流编号则让 Mac 重建解码器。上一轮优化仅消除了发布端编码器重建，未消除这些接收端重启。

现在用采集完成后发布的快照核对帧。画布内部的子窗口移动、菜单和弹窗变化是视频内容，尺寸和可见性不变时不推进网络几何版本，也不丢弃有效 P 帧。真正尺寸变化仍先发布新元数据，再发送匹配的关键帧；与最新快照不匹配的过期帧仍被拒绝并触发恢复。尺寸、可见性、标题及内部布局快照分别按需要更新。

没有修改网络恢复定时器、队列容量或 Mac 协议。先前怀疑的 500 ms 队列恢复路径不是本次复现日志中的触发来源。

## 验证

人工窗口 `windows-composed-motion.ps1` 在固定画布内每约 100 ms 移动一个所属子窗口。独立发布进程通过本机管理通道采集 240 帧，60 fps 上限、全色度；顺序运行诊断旧版和修复版：

| 指标 | 旧版 | 修复版 |
| --- | ---: | ---: |
| 视频流数量（含首流） | 39 | 1 |
| 网络几何版本数量 | 39 | 1 |
| 本机交付帧率 | 40.39 fps | 43.26 fps |
| 最大帧间隔 | 44.43 ms | 34.50 ms |

这个 WinForms 动画没有稳定提供 60 个新画面/秒；该测试用于证明不再反复开流，不代表跨 EasyTier 到 Mac 的帧率或呈现延迟。

- 合成快照测试覆盖尺寸变化、同尺寸内容变化、真正过期帧，检查元数据顺序及 P 帧连续性。
- 实际采集、编码和发布循环：硬件路径 120 帧、20 个布局版本、1 条视频流；强制 CPU 合成/软件编码 120 帧、21 个布局版本、1 条视频流。
- 两条人工窗口 H.264 码流分别经 FFmpeg `-xerror` 独立解码，无错误。
- Windows 检查脚本包含真实配对 QUIC、采集挂起时的连续输入、网络堵塞后的独立控制通道和关键帧恢复测试。

复现命令：启动该 fixture 后设置其 `PANEFERRY_COMPOSED_MOTION_PID`，运行 `cargo test --release --locked -p paneferry-windows --lib moving_owned_window_preserves_encoded_reference_chain -- --ignored --nocapture`。可选 `PANEFERRY_VIDEO_PROBE_DIR` 只导出这个专用人工窗口的视频，供独立解码检查。
