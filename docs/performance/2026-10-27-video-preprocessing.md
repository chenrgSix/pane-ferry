## 原先的“编码约 5 ms”包含什么

它指的是**整个编码调用**，并非 x264 本身。新增计时不增加管线元素，不映射视频像素，
在 appsrc、补边、颜色转换、编码器、appsink 的原有 pad 边界采集单调时钟和当前线程 CPU 时间。
同一 Encoder 同时只有一张输入，通过区间嵌套唯一关联最终响应的 RWP 帧 ID；不是把不同行的分位数拼起来。

下表来自最后一组旁路诊断，原版 40 条最终响应帧，单位 ms：

| 阶段 | P50 | P95 |
|---|---:|---:|
| 输入缓冲封装 | 0.006 | 0.013 |
| 输入就绪 → GStreamer 流线程开始 | 0.029 | 0.056 |
| RGB 补成编码所需偶数宽高 | 1.510 | 3.252 |
| BGRx → I420 颜色转换 | 2.155 | 3.964 |
| H.264 编码器 sink → src | 1.599 | 3.283 |
| 编码器输出 → appsink | 0.044 | 0.091 |
| appsink → 调用线程取回 | 0.023 | 0.049 |
| 提取编码数据 | 0.004 | 0.011 |
| 整个编码调用 | 6.030 | 9.346 |

**各行独立分位数不能相加。** 当前线程 CPU 并不包含编码器/转换器其他工作线程的 CPU 总量。
补边与转换的墙钟接近其流线程 CPU 时间，主要是在做实际工作；这几段排队、封包等待已经很小。
真实 H.264 编码约 1.6 ms，不是整个约 6 ms 都在压缩。

## 试验二：批量复制 RGB 黑色补边，未采用

[GStreamer 1.28.2 videobox 实现](https://github.com/GStreamer/gstreamer/blob/1.28.2/subprojects/gst-plugins-good/gst/videobox/gstvideobox.c)

## 当前更大的等待与历史 75 ms 的边界

当前原版的最后一组旁路诊断：Agent 收到输入到 GTK 收到约 **27.3 ms**；
应用绘制到首个响应读回完成约 **27.5 ms**，其中最终响应帧读回约 **13.0 ms**；
网络/桥接/序列化混合残差约 **29.0 ms**；Mac 解码约 **2.3 ms**，选帧到显示缓冲匹配约 **10.3 ms**。
这些区间可能重叠，分位数不能相加，混合残差也不能全部命名为网络。
余下的主要优化对象应是输入投递、采集调度及链路，而非继续微调约 1.6 ms 的编码器。

历史 75 ms 不能直接作本轮基线。上轮收尾 ICMP 平均约 7.7 ms；本轮两组开始前分别约 17.3、17.5 ms，
收尾约 29.1 ms，均为 `utun4` 路由。源端已有工作负载保留，逐轮 loadavg 随记录保存。
即使这两组用同一代码基线，也不能把 158.3 → 111.4 ms 当成任何一个候选的收益。
RTT 只是前后取样，不能据此独立解释所有波动或推算每条输入的单向网络时间。

## 测量条件与验收

- 相同自有 GTK X11 输入计数夹具，源 backing 2940×1618、2×，输出 1470×809、1×；每 33 ms 小块动画。
- 协商上限 30 FPS；H.264 质量、GOP、同一 Mac 宿主/网络程序、硬件解码均保持一致。
- 正式 Mac 显示区 1465×804 点、屏幕 60 Hz；初始诊断显示区略有不同，单独记录，不并入正式比较。
- 每组 8 轮旧、新、新、旧、新、旧、旧、新；每轮按键和点击各预热 2 次，再各 30 次正式采样。
  每条均验证输入计数、源绘制、最终视觉计数、分辨率、帧率与硬解，无失败轮次或尖峰被丢弃。
- 正式使用冻结的未插桩隔离 Agent 与原网络程序；真实输入和视频经过 QUIC，SSH 仅管理测试及取回日志。
  未在正式采样期间编译、运行门禁或系统性能跟踪。
- 起点是 Mac 输入处理函数，终点是 renderer 对应显示缓冲身份匹配；不含外设、屏幕扫描和面板响应。
  两端各自的单调时钟区间分别计算，未作无时钟映射的跨机器单向减法。
- 两个修正后的候选分别通过 Agent 45 项普通单测及 10 项显式 Linux/GStreamer 测试。
  这些通过不等于端到端性能验收通过。
- 正式未插桩数据缺少的首个读回/I420 关联 ID 保持空值；最慢五条保留输入 ID、最终 RWP 帧和可得时间线。
  诊断另有首个响应读回 ID、最终读回 ID及逐帧颜色转换/编码关联。
