# RustDesk / UU 远程流畅度调研

调研日期：2026-10-30。PaneFerry 基准提交：`d2097d60cd385e9a6cde61561de150167369468c`，同时检查当前工作区。RustDesk 源码固定于 `ef827fdb34aef13cb37826b9efc62e8b9a28f1b0`。这是源码与公开资料对照，没有在用户这组 Windows / Mac 上进行三款产品的同步性能实测；源码能力不代表用户安装版本或当前连接一定启用了它。

## 结论

RustDesk 有可核实的低延迟工程设计：输入独立执行、显存纹理编码路径、软件编码实时配置、接收反馈与动态码率/帧率管理。这些设计减少处理开销和积压，能解释它为何具备流畅运行的条件，但不能单凭源码量化这次体验差距。

UU 官方能确认高帧率、4:4:4 真彩、可调码率和线路调优等产品能力；未找到足以验证其完整采集、编码、调度和传输实现的公开技术资料，不能把“零拷贝”“特定拥塞算法”“FEC”等推测当成事实。

PaneFerry 当前的重点应是减少 Windows 侧同步处理和端到端等待，而非继续提高帧率上限。没有音频不意味着画面链路就低延迟；音频缺席不会消除视频的拷贝、计算、队列和显示等待。

## 已核实的 RustDesk 实现

### 输入不依赖视频编码循环

`connection.rs:713` 创建输入处理线程，`handle_input` 分派鼠标、键盘等事件；视频服务由独立服务线程执行。视频编码慢时，输入注入不必等待同一次编码调用结束。独立线程不代表完全没有锁竞争或网络排队。

来源：[输入线程](https://github.com/rustdesk/rustdesk/blob/ef827fdb34aef13cb37826b9efc62e8b9a28f1b0/src/server/connection.rs#L713)、[服务线程](https://github.com/rustdesk/rustdesk/blob/ef827fdb34aef13cb37826b9efc62e8b9a28f1b0/src/server/service.rs#L301)。

### 支持纹理直接编码，也保留软件路径

Windows DXGI 采集封装支持输出纹理；VRAM 编码器接收纹理而非强制转成 CPU 像素数组。符合条件时，可以绕过完整画面的 CPU 回读和 CPU 色彩转换。这里不宣称全链路绝对零拷贝，驱动内部仍可能复制或同步。

硬件库列出了 Intel QSV、NVIDIA NVENC、AMD AMF 等 Windows 路径，包含 RAM 和 VRAM 输入。软件 VP8 / VP9 编码另有实时模式、速度配置、多线程设置；视频服务存在编码器失败后回退 VP9 的逻辑。并不要求独立显卡，也不能保证每台机器都能高分辨率高帧率。

来源：[DXGI 输出](https://github.com/rustdesk/rustdesk/blob/ef827fdb34aef13cb37826b9efc62e8b9a28f1b0/libs/scrap/src/common/dxgi.rs#L60)、[纹理编码](https://github.com/rustdesk/rustdesk/blob/ef827fdb34aef13cb37826b9efc62e8b9a28f1b0/libs/scrap/src/common/vram.rs#L100)、[硬件矩阵](https://github.com/rustdesk-org/hwcodec#codec)、[软件编码](https://github.com/rustdesk/rustdesk/blob/ef827fdb34aef13cb37826b9efc62e8b9a28f1b0/libs/scrap/src/common/vpxcodec.rs)。

### 根据反馈调节生产速度和画质

`video_qos.rs` 使用视频流内的延迟探针观察排队，区分连接基线和额外延迟，动态调整帧率及码率比例。`video_service.rs` 还有帧接收通知和等待机制。它并非只按用户设定帧率不断生产画面，也不能笼统说它从不等待或从不重复编码。

没有新画面时有专门处理，静态刷新模块会按编码器和质量条件重复编码以改善静态质量。因此适合借鉴的是区分真实更新、必要质量刷新和无效重复工作。

来源：[QoS](https://github.com/rustdesk/rustdesk/blob/ef827fdb34aef13cb37826b9efc62e8b9a28f1b0/src/server/video_qos.rs)、[接收反馈](https://github.com/rustdesk/rustdesk/blob/ef827fdb34aef13cb37826b9efc62e8b9a28f1b0/src/server/video_service.rs#L1009)、[静态刷新](https://github.com/rustdesk/rustdesk/blob/ef827fdb34aef13cb37826b9efc62e8b9a28f1b0/src/server/video_service/static_refresh.rs)。

## UU 官方资料能确认什么

官网的高清画面页明确介绍 4:4:4 真彩、最高 144 帧和最高 500 Mbps 自定义码率，同时列出设备限制，并说明真彩模式可能受性能影响而卡顿。这些是能力上限，不是用户当前连接的实测帧率、码率或延迟。

这为清晰度差异提供了一个可能因素：PaneFerry 目前为 NV12 / 4:2:0，颜色细节的采样低于 4:4:4。保持源窗口尺寸只约束尺寸，不等于无损或保留全部色彩细节。不过用户所说整幅画面模糊还可能涉及压缩、缩放、实际编码尺寸及显示比例，需要实测区分；不能归因于色度采样一项。

官网还介绍线路智能调优和全球节点，但不能据此确认本次 UU 会话使用哪条路径。相同物理网络和设备不保证 UU、RustDesk 与 EasyTier 内 PaneFerry 的实际路径完全相同。

来源：[UU 高清画面及设备限制](https://uuyc.163.com/features/color/)、[UU 远程办公及线路能力](https://uuyc.163.com/features/work/)。网页工具无法读取时，已使用 HTTPS 命令行直接读取这两个 `163.com` 官方页面，没有使用搜索结果中的仿官网域名。

## 对照 PaneFerry：确定的结构问题与待测影响

| 环节 | 当前实现证据 | 对流畅度的意义 |
| --- | --- | --- |
| 输入与视频 | `apps/windows-node/src/lib.rs:491,612`：同一循环处理输入与同步采集/编码，发送完成前不返回循环 | 输入已有优先级，但无法抢占进行中的一次视频处理；实际等待时长尚未测量 |
| 采集回读 | `crates/backend-windows/src/native/capture.rs:154`：CopyResource、Map、复制到新 Vec | 每帧包含 GPU→CPU 同步及内存复制；WGC 本身不是已证实的瓶颈 |
| 窗口合成 | `scene.rs:264`：缓存各窗口像素，每次分配输出并合成，即使没有新采集帧 | 主窗口、弹窗和菜单需要合成，但可以减少分配、重复合成及回读 |
| 编码输入 | `pixels.rs` CPU 转 NV12；`video.rs:34,80` 固定软件 MFT，新建输入缓冲并复制 | 没有硬件编码选择；现有低延迟、零 B 帧配置应保留 |
| 本地通信 | 发布端将 H.264 base64 放入 JSON；网络层解码，接收本地接口再恢复 | 有额外序列化、解析和分配；网络 RWN/2 已用二进制视频，不应误称网络带宽额外增加 1/3 |
| 流控 | `video_flow.rs` 最多 6 帧未确认，Mac 反馈约 50 ms，500 ms 超时重启编码 | 已有保护，但缺少结合实际排队时间的动态码率控制；6 帧是上限，不代表固定等待 100 ms |
| Mac 解码显示 | VideoToolbox 解码，每包等待异步帧完成；每流保序；解码后旧画面可合并；CVPixelBuffer 直接显示 | 不是整条链路都走 CPU；还需测等待与调度。主线程已有事件唤醒，90 Hz 定时器并非唯一交付方式 |

`VideoDecodeQueue` 的 64 个任务 / 24 MiB 是总保护上限，不是实测积压量。显示反馈来自 CATransaction 完成，不能当作物理屏幕已经扫描显示的时间。

先前 60.29 fps 是本地交付吞吐测试，包含重复画面，不包含 EasyTier、Mac 解码及显示，不能证明端到端动态 60 fps。已有 CPU 转换 / 软件编码耗时测试可作为优化前基线，但不足以排定全部瓶颈。

## 建议顺序

1. **先建立端到端时序和动态画面基线。** 记录新采集帧、合成、转换、编码、发送等待、接收、解码和提交显示的时间及队列长度。报告独立画面帧率、帧间隔 P50/P95/P99、输入到视觉反馈延迟；不同机器的时钟需校准，或用同一相机观测输入与画面，不能直接相减未同步时钟。
2. **隔离输入与视频处理。** 输入执行不等采集、编码或视频发送；移动事件可合并，按键/按钮边沿需保序。保留焦点、权限和弹窗目标校验。
3. **优化软件基础路径。** 复用像素与编码缓冲；评估向量化色彩转换；跟踪画面和布局变化，减少无更新时的全量合成；本地视频接口逐步改二进制。必须保留必要的静态质量刷新。
4. **用排队时间控制负载。** 在编码前选最新原始画面，拥塞时自适应码率/帧率；已编码的 H.264 P 帧不能随意丢弃，否则会破坏参考关系，应结合关键帧恢复。
5. **增加可选硬件路径。** 自动探测核显/独显能力，有条件时在 GPU 完成应用窗口合成、色彩转换和编码；不支持或失败就用软件路径。绝不绑定 NVIDIA 或要求独显。
6. **清晰度单独验收。** 核对源像素、编码尺寸、Mac 显示比例与动态码率，再评估可选 4:4:4。原画尺寸与无损画质分别定义，不能靠提高码率掩盖其他问题。

保持用户要求：在 Windows 合成主窗口、弹窗和菜单后传送同一应用画面。RustDesk 的常规桌面采集可以利用系统已合成的桌面，我们有额外的应用场景合成工作；这说明优化对象不同，不意味着必须改成整桌面共享。

验收比较需固定分辨率、帧率、画质/色度格式、窗口内容与显示刷新率，并记录实际路由、编码器及 CPU/GPU 占用。分别测试滚动、拖动、浏览器视频全屏、弹窗菜单、单窗口和多窗口。当前调研未修改运行代码、重启服务或推送提交。
