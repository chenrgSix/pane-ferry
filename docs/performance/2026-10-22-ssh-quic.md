# SSH 与 QUIC 的实机对照

2026-10-22，Apple Silicon Mac 与 Ubuntu 26.04.1，目标 `10.0.1.66`。**当前不建议移除 SSH：两者功能和短时恢复都通过，但速度有场景差异，QUIC 动态画面的尾延迟仍高于 SSH。** 这比较的是本项目当前实现与当前网络路径，不是两个协议在所有环境下的排名。

## 方法

同一源码、相同 2560×1664 窗口和编码配置、真实 H.264、VideoToolbox 硬件解码及 AppKit 绘制。两端网络组件和临时 Agent 使用 release 构建；不更改已安装服务。每轮方向键、文字提交、点击各 30 个有效样本，另有各 2 次预热；共 **6 轮、540 个有效样本**，36 个预热样本不计入。

顺序为 SSH 动态 → QUIC 动态 → QUIC 动态 → SSH 动态 → SSH 静止 → QUIC 静止。动态组采用相反顺序各测两轮，全部纳入统计；静止组各一轮。未筛选快速样本，也未拿前一天的性能数字混作此次对照。另一次早期测量因旧测试钩子不匹配当前界面代码，在启动测量前失败；修正测试工具后重新执行，未产生或纳入性能样本。

起点是产品 `SurfaceView` 输入处理函数，终点是对应输入标记实际完成 `NSImage.draw`。每个样本均核验画面标记、输入类型、尺寸、H.264 和硬件解码；不包含拼音组合、键盘硬件、最终系统合成和面板扫描。SSH 复用已认证连接；QUIC 复用已配对连接。两者均排除首次认证、配对、首关键帧与首次解码器分配，测量日常交互而非冷启动。

读取目标路由确认两者走当前 **utun4、MTU 1360**。没有切换路由、关闭虚拟网络、模拟丢包或限速；后台负载未完全固定。因此静止组的单轮优势和动态组的尾延迟不能推广为所有直连局域网的表现。QUIC 模式的 SSH 仅管理临时测试进程、构建和收集日志，输入及视频不经 SSH。

## 延迟结果

单位 ms；P95 为 95% 样本不超过的耗时，数值越低越好。动态组每种传输 180 个样本，静止组每种 90 个。

| 场景 | SSH 中位数 | QUIC 中位数 | SSH P95 | QUIC P95 |
| --- | ---: | ---: | ---: | ---: |
| 持续更新窗口，两轮合并 | 93.01 | 113.83 | 147.19 | 213.38 |
| 静止窗口后输入 | 83.46 | 67.86 | 166.26 | 99.72 |

本次动态组 QUIC 中位数约高 22%，P95 约高 45%；静止组中位数约低 19%，P95 约低 40%。不能据此称为“差不多”，也不能笼统断言 QUIC 更快或更慢。

| 动态独立轮次 | SSH 中位数 / P95 | QUIC 中位数 / P95 |
| --- | ---: | ---: |
| 首轮，SSH → QUIC | 83.12 / 116.51 | 117.16 / 301.40 |
| 复测，QUIC → SSH | 101.43 / 157.39 | 104.93 / 196.07 |

传输、桥接与读取缓冲剩余段的动态组中位数/P95 为 SSH **15.30 / 60.15**、QUIC **32.66 / 140.67**；静止组为 SSH **23.50 / 111.71**、QUIC **9.06 / 39.86**。这是同机时钟的完整往返扣除两端内部阶段，不是单向网络延迟，也不能独自定位成 UDP、拥塞算法或某个缓冲区的问题。

QUIC 静止轮的发布端连接统计记录 597 个发送包、0 个丢失包、0 次拥塞事件，末次估计 RTT 14.88 ms、最小 RTT 5.77 ms、探测 MTU 1326。计数覆盖该临时连接生命周期，包含配对和预热；不能拿它证明动态轮没有丢包，或认定没有抖动。

## 稳定性、功能与成本

| 项目 | 当前证据与边界 |
| --- | --- |
| 双向基本功能 | SSH 与 QUIC 均通过真实两机发布/接收、输入、缩放、文本剪贴板、同会话恢复；详细范围见验证记录 |
| 重复恢复 | 两者各 **20/20 次**逻辑会话断开、等待 1 秒、重连恢复通过，原窗口/状态保持；包括按住输入断开释放。不是拔网线、Wi-Fi 切换或传输服务重启测试 |
| 同时双向 | QUIC 反向 H.264 连续 30 秒保持 ready 和连接代次，同时正向完成输入及三次重连 |
| 多设备 | 本机三节点配对、撤销隔离通过；没有三台以上物理设备的完整并发验收 |
| 配置与依赖 | QUIC 可用设备邀请直接配对，不需要对端 SSH 登录；SSH 需要账号、主机身份验证及反向共享通道 |
| 数据与并发 | QUIC 分控制、每窗口可靠视频和低优先级文件流；视频使用二进制，去掉 base64 膨胀。本机仍有 JSON/base64 适配；大文件的 SSH 通道原本也是二进制 |
| 总流量、CPU、内存 | 尚未完成同条件量化，不能用宿主收到的 JSON 行长度推算网卡流量或 CPU 收益 |
| 长期与弱网 | 长时间运行、系统休眠、物理断网、地址迁移、丢包/拥塞、UDP 受限网络尚未完成对照；不能称为稳定性完全等同 |

## 建议

继续以 QUIC 作为产品的主线，保留当前 SSH 显式兼容入口。先定位并改善动态窗口的传输长尾，再补真实断网/休眠/网络切换及日常持续运行验证；在这些结果接近现有 SSH 体验之后，再移除产品中的 SSH 依赖。此次没有删除 SSH，也没有把 QUIC 失败自动回退到 SSH，因此以上 QUIC 样本没有混入兼容链路。

删除产品内 SSH 传输，与使用 SSH 维护 Ubuntu 是不同范围。后者仍可作为开发/部署工具，不能因为测试脚本使用 SSH 管理进程，就说产品 QUIC 依赖 SSH 才能连接。
