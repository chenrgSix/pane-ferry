# Windows GPU 纹理直接编码

本轮接续 `a0180ae`，将 GPU 合成、色彩转换的结果直接送入支持 D3D11 的系统硬件 H.264 编码器。PaneFerry 在这条路径上不再将原始画面回读到 CPU，也不再为编码器重新上传原始像素；压缩后的 H.264 码流仍需取回并发送。WGC 表面到合成纹理仍有显存内复制，因此不声称所有组件内部都完全没有复制。

## 设备与资源生命周期

- 使用采集设备的 DXGI adapter LUID 枚举硬件 MFT，检查 D3D11-aware 属性，并通过 DXGI device manager 绑定同一设备。没有厂商专用 SDK 或独显要求。
- 共享 D3D11 immediate context 启用多线程保护，NV12 的 Y、UV 视图由计算着色器直接写入。4:2:0 和 `444-atlas-v1` 均复用上一轮相同的整数色彩公式。
- 输入纹理池最多保留三个槽位。每个输入使用 `IMFTrackedSample`；MFT 释放输入样本并触发回调之后才能复用对应纹理，不以“已经收到输出”推断输入已释放。
- 编码器通过 `BeginGetEvent` 回调唤醒等待线程，取消原来每帧的 1 ms 轮询等待；仍保留 100 ms 超时和单个在途输入限制。
- 改变尺寸时旧纹理由未释放的输入继续持有，新尺寸使用独立纹理池。纹理池耗尽、设备/编码器错误或等待超时会进入软件回退，不覆盖正在使用的纹理。
- 创建支持视频的 D3D11 设备失败时，仍尝试普通采集设备，避免给软件编码增加硬件视频能力要求。

## 选择与回退

GPU 场景默认尝试纹理硬编码；`PANEFERRY_VIDEO_ENCODER=software` 强制软件编码，`auto` / `hardware` 允许硬件发现但仍保留回退。`PANEFERRY_VIDEO_GPU=off` 强制 CPU 合成。没有 GPU 合成时，未设置编码器环境变量仍默认软件编码。

初始化不支持当前尺寸/格式时使用软件编码；运行中硬编码失败则读回当前已合成画面，建立新的软件编码流并输出 IDR。会话内不反复重试失败的硬编码器。4:4:4 模式和源窗口尺寸保持不变，网络协议、授权窗口范围和弹窗输入路由不变。

这是对系统驱动能力的探测和适配，并不保证所有核显/独显驱动、任意小窗口都支持硬编码。本机 64×48 测试被驱动拒绝，软件路径可用；320×180、1602×932、2560×1440 的普通及全色度模式均完成真实纹理硬编码。

## 验证

- GPU NV12 纹理回读仅用于测试，与现有打包 NV12 输出逐字节比较；覆盖奇数尺寸、透明合成、叠加和两种色彩模式。
- 保留三个输入后第四次分配明确失败，释放后才可复用；硬件连续编码每种尺寸/模式 120 帧验证实际回调回收。
- 真实动态窗口在纹理硬编码下输出视频；最大化、还原及 60/1/5 fps 的六次切换通过。
- 专用测试在运行中的硬编码器注入一次输入失败，验证软件回退后的新流号、IDR、源尺寸及后续连续输出。注入入口仅编译到单元测试中。
- FFmpeg 独立解码硬件生成的 4:4:4 视频，无 B 帧。1602×932 单像素红蓝线样本首帧的 Y/U/V 平均绝对误差分别约 0.657、0.506、0.000043，最大误差 2；不是任意桌面的画质保证。
- `windows-444-atlas-hardware.json` 是 320×180 人工红蓝线样本的真实硬编码首帧，Mac 解码检查同时覆盖此样本和原有软件编码样本。

`gpu.convert_texture_submit` 只记录提交时间，GPU 完成与编码器等待包含在 `video.encode_texture`。所有本机测量均不等于 EasyTier 到 Mac 的实际端到端延迟。

事件唤醒版在同一台机器的 1602×932 动态测试窗口读取 240 帧：4:2:0 / 全色度分别交付约 60.14 / 60.13 fps，帧间隔 P95 约 19.75 / 19.02 ms。普通模式稳定计时区间的单次处理 P50/P95 为 2.082/2.437 ms；此前软件编码版本的顺序对照为 2.788/3.572 ms。全色度对应 3.249/4.326 ms。区间包含无帧调用，内容运动与系统调度并非完全相同，不据此推断真实 Mac 端的延迟改善比例。

已在正式 Windows 发布端验证 `PF_ENCODER backend=hardware input=d3d11_texture`，仍监听 UDP 42424，部署前后身份文件摘要相同。强制 CPU 合成及软件编码的 4:4:4 真实窗口测试、硬编码运行时故障回退、硬编码菜单合成与点击均通过。
