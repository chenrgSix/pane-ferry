# 私有 GPU 缓冲接入正式 Linux Agent

**X11/XWayland 路径已接入，并更新本机正式 Agent。** 最终交错对照中，自动模式两轮均选择 GPU：
2940×1618 自有滚动窗口的采集到本机 socket 写出 P50 从 **44.97 ms 降到 33.41 ms（−25.7%）**，
发布吞吐从 36.75 提高到 **40.63 FPS（+10.5%）**。这是本机夹具结果，不是远端显示延迟或所有负载的收益保证。

[完整统计](2026-10-28-agent-dmabuf-integration.json)、
[全部对照、失败记录、逐帧关联、构建/测试日志及源码快照](2026-10-28-agent-dmabuf-integration.raw.json.gz)。
接续[独立原型验证](2026-10-28-dmabuf-validation.md)；原型的约 38% 不直接套用到发布链路。

## 正式实现

- 异步采集可以返回不可变 `VideoCapture::DmaBuf`。只导出 Agent 自己的私有目标，
  仍核对源窗口几何、进程身份、DRI3 导出对象身份、stride 和 GPU 完成 fence。
- `Frame` 将租约交给 GStreamer；`GstMemory` 的 qdata 保留 `Arc<DmaBufFrame>` 至最后一个内存引用释放。
  目标池最多四个，租约未释放时不覆盖，满时保留 Damage 重试。窗口代际与已退休编码结果的丢弃规则继续生效。
- BGRx DMA-buf → `vapostproc` → VA NV12 → `vah264lpenc`，不在该 GPU 阶段生成 CPU 像素快照。
  CPU 映射和不可变快照只在软编实际需要时建立；普通 Xvfb/SHM 和原生 PipeWire I420 继续使用原路径。
- 存储宽度按 16 像素对齐，当前驱动对应 64 字节 pitch 对齐；可见尺寸不变。
  奇数宽高在私有 GPU 目标中补黑边至偶数，VA 输入采用实际 stride 和偶数编码尺寸，保持原可见像素。
- 固定时间戳在 VA 转换前按 DMA-buf 的实际字节数生成，避免 VA 池的对齐大小改变时间戳。
  超过 identity 有符号字节率上限的大图/高帧率组合使用软编。名义码率、QP 上限 28、GOP 与无 B 帧设置保留。
- 首帧 GPU 失败在发出第一个包前改用软件；已发布流失败时用新的 stream ID 和 IDR 重启软件编码。
  当前包保留自己的流标识，不会被下一帧的路径切换改写。不可恢复错误仍执行原有断开与输入释放。

实现位于 `crates/backend-x11/src/{linear_capture,render_scale,video_capture,async_capture,readback}.rs`，
及 `apps/linux-agent/src/{video,video_frame,video_dmabuf,video_choice,output_worker}.rs`。
线上协议、网络组件与客户端代码没有改变。

## 默认自动选择，避免硬编争用造成回退

本轮实际出现过显卡负载很重时硬编更慢的情况，不能无条件启用：

| 同组高负载交错对照 | 采集 → 写出 P50 / P95 | 发布 FPS |
| --- | ---: | ---: |
| 强制 CPU | 77.01 / 106.86 ms | 15.25 |
| 强制 GPU | 84.55 / 122.83 ms | 12.69 |

GPU 编码本身较快，但当时采集等待增加，整条链路反而变慢。
不同组的绝对时间变化很大，不能将高、低负载组互减为优化收益。
另一个只按总延迟选择的候选虽然 P50 略降，吞吐却下降；还测试过保留 GPU 租约、仅让编码器软编的候选，
也有回退。因此最终实现同时约束延迟和瓶颈，并在选中软件后恢复采集端的原 CPU 快照路径。
这些有效对照和失败轮次均保留，没有只选快的结果。

默认策略对每个新窗口流：

1. 编码 16 帧软件、16 帧 GPU，各跳过前 4 帧，比较其余 12 帧的中位数。
   每帧只编码一次，不额外复制一份画面做并行对照；静止重复帧沿用软件像素去重，不计作编码样本。
2. GPU 的采集到编码完成时间至少快 8%，且采集/编码瓶颈服务时间不恶化超过 3%，才保留 GPU。
   瓶颈用采集完成时间与编码线程服务时间的较大者估计，不等同于直接测得的全链路 FPS。
3. 保留 GPU 后继续观察；总耗时超过软件基线 15% 或瓶颈超过基线 10% 时改用软件。
   软件选择通过绑定窗口 epoch 的共享标志传回采集 worker，后续帧恢复经典 CPU 采集。
   旧窗口/控制端的迟到决定不能改变新 epoch 的选择。
4. 新几何或重新建立流后可重新比较。软件模式保留像素去重，GPU 模式只依赖 Damage，避免为了比较像素而读回整帧。

`PANEFERRY_VIDEO_GPU=0` 禁用 GPU 帧路径；`=1` 跳过性能比较直接尝试 GPU，仍有错误回退；未设置为上述自动模式。
短期采样不能保证在任意动态负载下始终最优；切换/试跑有启动成本。相关阈值和异常输入场景有独立单元检查。

## 最终发布对照

同一个诊断构建，仅切换 CPU/自动模式；独立私有 GNOME/XWayland、自有 GTK 连续滚动，
2940×1618、60 FPS 协商上限，反馈关闭。CPU / 自动 / 自动 / CPU 顺序运行，双方均预热 5 秒、统计 8 秒。
延长预热用于排除启动试跑，原始启动数据仍保留。没有并行编译或运行其他自建基准；用户其他任务保持运行。

起点是读回函数入口，含 X11 验证、私有目标渲染与等待；终点是完整 H.264 JSON 行写入本机 Unix socket。
每个已发布帧按采集 ID、消息 seq、字节数和时间单调性关联，不能用吞吐代替单帧耗时。

| 路径 | 计时帧数 | P50 / P95 | 发布 FPS |
| --- | ---: | ---: | ---: |
| CPU | 588 | 44.97 / 64.48 ms | 36.75 |
| 自动选择 GPU | 650 | **33.41 / 50.75 ms** | **40.63** |

各轮 P50 / FPS：CPU **47.20 ms / 36.00**，自动 **33.56 / 40.50**，自动 **33.10 / 40.75**，CPU **42.93 / 37.50**。
合并同模式逐帧样本后计算分位数，不平均分位数；FPS 按等长统计窗汇总。
两轮自动试跑的内部 CPU/GPU 中位数分别为 60.3/33.1 ms、56.4/35.9 ms，最终保留 GPU。
这些启动基线也不应当代替表中的预热后 CPU 对照。

全部 **1238 个计时帧**均进行解码后的源计数关联和顺序检查。
CPU 两轮共解码 949 帧，自动两轮共解码 1053 帧，包含预热和合法 IDR 流切换。
解码在统计结束后执行；单流使用 OpenH264，多流切换使用 FFmpeg。
初始尺寸变化后可能先发布空白表面，无法对应 GTK 计数的预热帧单列；计时帧不允许缺失或倒序。

## 回归、画质与失败记录

- 工作区标准测试 **129 项通过**；另显式执行 **11 项** GStreamer 回归，包括原生 I420 裁剪、异步唤醒、
  源租约释放、首帧回退和中途 GPU 失败后新流/IDR。
- GPU 私有 pixmap 检查验证四目标背压、复用、resize、旧目标退休后租约仍保持原像素，以及奇数尺寸黑边。
  另一个实际采集 worker 检查验证选择软件后返回 CPU 图像，旧 GPU 帧仍可保持原像素。
- 在私有合成器中，2800×1500、1470×809、641×483、2940×1618、900×701 的 IDR 独立解码通过；
  重连保持原测试应用和内容。六个静态窗口全部通过四目标池发布，未出现旧输入引用占满目标池而饿死后续窗口。
- 125%→100%→125% 缩放、2× 源窗口、奇数高度、正常控件尺寸、对话框及嵌套弹窗检查通过。
- 长期用户目录中的 VA 运行时另跑了完整功能跟踪：13 帧均为 DMA-buf/VA，13 次 PRIME2 导入，
  未观察到输入 DMA-buf 的 GStreamer CPU 映射或 VA 输入 image 映射；VA map 是压缩码流读取。
- 一次单 IDR 的 OpenH264/GStreamer EOS 检查没有输出。保留码流后，FFmpeg 独立解码成功；
  SPS 明确 `max_num_reorder_frames=0`、DPB=2，连续 OpenH264 流也通过。独立 IDR 检查改用 FFmpeg，
  没有通过增加编码延迟来“修复”它。未对本次码流重新做 macOS VideoToolbox 实测。
- 一次完整 GNOME 冒烟在既有的平移指针边界检查失败；没有将完整冒烟报告为全绿。
  原生视频部分、专门的视频/缩放/弹窗检查及解码验证分别通过，失败日志保留。
- 早期一轮计数关联失败使对照不完整，未纳入性能统计；后续逐帧计数明细在断言前落盘。
  中间候选、构建生成失败和不利性能结果均在原始归档中。

## 本机更新与边界

已原子替换 `~/.local/bin/paneferry-agent` 并重启原 `remoteapp-agent.service`：**PID 2160857，active，NRestarts=0**。
重启前确认活动会话为 0；网络服务保持 **PID 8101**，未重启。新 ELF 与运行进程映像 SHA-256 均为：

`621e55075e6b66a47aec00d9f5655a407a6afce0cc7be4562c999665845f1bcd`

旧 ELF 保存在 `~/.local/bin/paneferry-agent.before-dmabuf-20261028`，SHA-256 为
`f542fdb14c8c272c32ba22025247c01b31688dc222fd3f6bef31da4dd0d8fc20`。
安装的是无插桩正式构建，诊断构建哈希不同。

本机原来缺少可用的 Intel VA 运行时。本次将已验证的 Ubuntu iHD/GMM 库及版权文件放入
`~/.local/lib/paneferry/va-26.1.2`，通过用户服务的 `85-paneferry-va.conf` 提供库路径、驱动路径和独立 GStreamer registry。
没有安装系统包、改桌面显示设置、电源/时钟、跟踪权限、网络配置或用户应用资料。
Agent 代码自身不会下载或安装驱动；其他机器仍按可用组件选择软件/硬件。

范围仅为本机 Intel UHD 730 与自有夹具；没有采集用户实际应用、注入用户桌面输入，
也没有测 QUIC、控制端解码/显示或最终扫描输出。GPU 转换、复制与 fence 等待仍然存在，不能叫作全链路零复制。
当前结果支持正式启用这条可回退路径，不能宣称所有 Ubuntu 应用始终提升 26% 或原型的 38%。
