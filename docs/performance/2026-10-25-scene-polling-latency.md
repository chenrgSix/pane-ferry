# 应用会话画面的采集等待诊断与调度优化

2026-10-25，真实 Mac → Ubuntu → Mac IDEA 菜单测试。修改：`b341169`；诊断工具：`74adb93`。

## 条件与可比性

同一个 IDEA 进程、Git 日志右键菜单、2940×1618 源像素、2× 缩放、同一 Mac 探针与 QUIC 网络服务。
观察菜单后选择源坐标 (1000,380)，ROI (1150,600,220,240)；只右键及 Escape，不执行菜单命令。
每次先视觉检查预览，等待关闭，再预热 2 次；正式构建每组 60 次。正式 A/B 的产品源码只差本次调度修改。
两组均为单应用会话画面、H.264、VideoToolbox 硬件解码；客户端产品代码未修改。

原先 221.522 ms 来自项目树菜单；本次 IDEA 重开后是 Git 日志布局，且有其他用户任务运行。
因此历史 222 ms 不能作为严格 A/B 基线。安装旧版的探索轮次也不能代替相同源码的正式基线。
测试保留当前运行的用户工作负载，没有关闭 RustDesk、用户 JVM 或其他应用。
Mac 到 Ubuntu 的实际路由为 utun4（EasyTier），不是宣称直连局域网的结果。

## 定位依据

初始 60 次诊断：输入排队中位数 0.021 ms，处理 2.920 ms，输入处理完成到匹配画面取帧 118.785 ms，
编码 6.726 ms，传输/桥接双向残差 38.060 ms，Mac 解码 16.988 ms。
主要等待位于远端画面产生与采集，而非输入流排队或编码。

进一步在原始与转换后 appsink 回调加时间戳。详细诊断 30 次中，输入后首个原始帧通知约 67.531 ms，
转换就绪到匹配画面取帧约 14.809 ms。应用会话模式仍在每次输入后，以 16.667 ms 的频率同步查询
窗口范围和场景信息；这些 RPC 与取帧共用控制线程，增加了转换完成后的等待。

优化将**已经建立的合成应用画面**的元数据查询保留为 100 ms。弹窗由 GNOME 每次绘制前合成，
PipeWire 回调独立唤醒视频采集，所以这不是把视频改成 10 FPS。初始画面发现和逐窗口模式仍采用
16.667 ms 快速扫描；自适应帧率、输入优先级、逐事件权限/坐标校验、窗口存活检查均保留。
适用于该模式的所有应用，无 IDEA 名称、进程或菜单特判。

同样 30 次的插桩试验中，转换就绪到取帧中位数降至 0.114 ms，完整菜单响应从 202.698 ms 降至
178.618 ms；输入到取帧从 124.311 ms 降至 99.594 ms，编码和解码耗时基本不变。
回调首个/最近时间是管线就绪线索，不能当成最终匹配帧的精确应用绘制时间；各阶段中位数也不可直接相加。
最终收益以下面无插桩正式构建的复测为准。

## 正式构建复测

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 端到端中位数 | 199.438 ms | 180.650 ms |
| 端到端 P95 | 246.924 ms | 233.878 ms |
| 响应区间中位数（发送结束→完整视频行收到） | 170.786 ms | 153.912 ms |
| Mac 解码中位数 | 16.952 ms | 16.074 ms |
| Mac 主线程等待中位数 | 6.353 ms | 4.523 ms |
| 绘制中位数 | 3.286 ms | 3.103 ms |

端到端中位数减少 18.788 ms（9.4%）。未降低源分辨率、画质或缩放。
两组均为 60 个正式样本、2 个预热样本，零匹配超时；所有样本仍只有一个本地应用画面窗口。
